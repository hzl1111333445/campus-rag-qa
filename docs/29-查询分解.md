# 查询分解：把"一句话两个意图"拆开再检索

> 状态：已实现、已实测（开关默认**关**，`DECOMPOSE_ENABLED=true` 打开）
> 代码：`demo/src/main/java/com/campus/rag/service/QueryDecomposer.java`（新增）、`RetrievalService.searchMulti()`（新增）、`QaService` 单轮分支（改）、`application.yml` 的 `campus.decompose.*`

---

## 1. 为什么要做

### 1.1 现象：复合问题一定答不好

问「助学贷款要准备什么材料，去哪个部门办」，系统原来的表现是：

```
topScore 0.3267、命中《入伍学费补偿》+《宿舍管理规定》、结论"本知识库未收录"
```

真正该命中的《国家奖助学金实施办法》《家庭经济困难学生认定办法》**没进前 3**。

### 1.2 根因不是模型笨，是"只问了一次检索"

一条查询同时含两个意图时，向量与 BM25 都在做"平均"：

- 向量是整句一个向量，「材料」和「部门」两个语义被混成一个点，落在两者中间；
- BM25 的词频被摊薄，"助学贷款"这个词的权重被"材料/部门"分掉。

结果就是**两个意图互相稀释，谁都进不了前 3**。这不是提示词能修的（提示词在看到资料之后才生效），必须在检索之前动手。

### 1.3 为什么不直接上 ReAct

| 方案 | 收益 | 成本 | 是否需要"看结果再决定下一步" |
|---|---|---|---|
| 查询分解（本方案） | 让每个意图各自检索一次 | +1 次轻量模型调用（约 0.3~0.5s） | 否 |
| ReAct 多步 | 还能"查完发现不对再查一次" | +2~4 次调用、1~3s、需要工具治理与 trace | 是 |
| 不做 | 复合题继续答偏 | 0 | — |

我们的问题分布是"单跳占九成"，真正缺的是"一句话两个意图"这一种情况。**先做便宜的，把 ReAct 留到需要多步验证时再上。**

## 2. 怎么做

### 2.1 四个改动

| 文件 | 改动 |
|---|---|
| `service/QueryDecomposer.java`（新增） | `decompose(question)`：把复合问题拆成 ≤N 个子问题；缓存；失败退回原句 |
| `service/RetrievalService.java` | 新增 `searchMulti(queries, topK)`：每个子问题各走一遍 prepare → 精排 → 展开，再按块去重合并 |
| `service/QaService.java` | 单轮分支：`subQueries.size() > 1 ? searchMulti(...) : searchBestGated(...)` |
| `resources/application.yml` | `campus.decompose.enabled`（默认 false）、`max-queries`（默认 3） |

### 2.2 三个关键设计

**① 便宜的预筛（`looksCompound`）**

不是每个问题都值得调一次模型。120 题单跳集里 **81 题长度 < 12**，如果每题都调，平均延迟 +0.5s 却没有任何收益。所以先用规则筛：

```
长度 ≥ 12  且  （有逗号/顿号/分号/问号  或  含"并且/还有/另外/同时/以及"）
```

不满足就直接返回原句，一次模型调用都不花。

**② 兜底必须"退回原句"，不能"猜"**

分解器内部 `try/catch` 全包，模型抽风、超时、拆出一堆废话时一律 `return List.of(question)` —— **宁可不分解，也不能把原本答对的题弄坏**。解析时还做了：去编号前缀、去空行、超 60 字丢弃、去重、第一行永远放原句。

**③ 合并规则要可复现**

同一块被多个子问题命中时取**高分**（`max`），排序 `score desc, chunkId asc`，上限 `max(topK, 5)`。为什么要塞 5 块而不是 3 块：多跳答案经常需要"A 文件的条件 + B 文件的后果"，3 块不够；但也不能无限加，5 块是实测下"够用且不稀释上下文"的量。

## 3. 结果

### 3.1 五道多跳题配对实测（同一实例、清空缓存后对比）

| # | 问题 | 关（原链路） | 开（查询分解） | 变化 |
|---|---|---|---|---|
| 1 | 专升本+绩点2.3+警告处分，能拿学位证吗 | topScore **0.011 → 直接拒答**（refs 0） | 0.2113，命中《学位授予细则》，答出"绩点 2.0 以上 + 记过及以上未解除才不授予" | **由误拒变可答** ✅ |
| 2 | 旷课被警告，还能评奖学金吗 | 0.3009，refs 3，2 份文档 | 0.3064，refs 3，2 份文档 | 持平 |
| 3 | 转专业后挂两门，还能再申请吗 | 0.4494，refs 1，**1 份文档** | 0.4436，refs 2，**2 份文档**（学籍规定 + 转专业办法） | 证据变宽 ✅ |
| 4 | 退伍复学，宿舍怎么申请 | 0.6686，refs 1，**1 份文档** | 0.7127，refs 3，**2 份文档**（入伍细则 + 宿舍规定） | 证据变宽 + 分数更高 ✅ |
| 5 | 助学贷款要什么材料、哪个部门办 | 0.0255，2 份文档（含《入伍学费补偿》） | 0.3158，2 份文档（奖助学金 + 入伍代偿） | **分数 12 倍，仍诚实说未收录**（数据缺口，见 §4） |

最关键的是第 1 题：**原来直接误拒，现在能答**——这是"拒答阈值太粗"的一个真实反面证据，也说明分解对"多条件单跳题"同样有效（原句把三个条件挤在一起，检索被拉偏）。

### 3.2 120 题单跳回归（清空缓存、冷启动，两次全量）

| 指标 | 关 | 开 | 判定 |
|---|---|---|---|
| gated 判定变化 | — | **0 道** | 无回归 |
| grounded 变化 | — | **0 道** | 无回归 |
| topScore 中位 / p95 | 0.7722 / 0.9907 | 0.7748 / 0.9906 | 基本不变 |
| 平均引用数 | 1.71 | 1.73 | +0.02 |
| 平均耗时 | 1376ms | **1386ms** | **+10ms** |
| 全量耗时 | 167s | 168s | 基本不变 |

**为什么延迟只 +10ms**：预筛把绝大多数单跳题挡在门外（120 题里 81 题长度不足），实际触发分解的只有少数题目。

### 3.3 一个必须记住的坑：缓存会污染 A/B

第一次跑 A/B 时，120 题**全是缓存命中**（`hits` 从 0 跳到 120），分解一次都没触发，得出的"无差异"毫无意义。正确做法：

```bash
# 每组跑之前必须清缓存
POST /api/dev/cache/purge?target=qa
```

**教训：任何 A/B 实验前，先证明"实验组真的走了新代码"，再谈结论。**

## 4. 边界与不做

- **不做 ReAct**：本方案只解决"一次问几个问题"，不解决"看了结果再决定下一步"。要后者请走 ReAct（+2.5 天）。
- **第 5 题仍然答不出**：库里没有《助学贷款》这份文档，分解再准也变不出材料。**数据缺口不能用算法补**（已记入 `docs/12-语料清单与缺口.md`）。
- **默认开关是关的**：多一次模型调用就是多一份成本与失败面；线上要开需同时确认：模型可用性、`max-queries` 合理、缓存命中率可接受。
- **子问题上限 3**：贪多会稀释上下文（5 块里塞 3 个意图，每个意图只剩 1~2 块）。
- **多轮路径没接**：多轮走的是"追问补全"分支，与分解互斥（同一句话在两个上下文里意思不同，先补全再分解容易双错）。

## 5. 复现命令

```bash
# 1) 启服务（打开分解）
$env:DECOMPOSE_ENABLED='true'
java -jar demo/target/campus-rag-0.1.0-SNAPSHOT.jar --server.port=8081

# 2) 清缓存（A/B 必需）
curl -X POST "http://localhost:8081/api/dev/cache/purge?target=qa" -H "Authorization: Bearer <token>"

# 3) 看日志里是否真的拆了
#    查询分解：「…」→ […, …, …]
#    多查询检索：3 路查询 → 合并后 5 块，最高分 0.3158
```

## 6. 一句话总结（面试口径）

> 复合问题答不好，不是模型不行，是**只检索了一次**——两个意图在一个查询里互相稀释。
> 我加了查询分解：先用便宜规则筛出"像复合句"的问题，再用一次轻量调用拆成 2~3 个子问题，各自检索后按块去重合并。
> 开关默认关，**120 题单跳集零回归、平均延迟 +10ms**；五道多跳题里三道的证据变宽，一道从"误拒"变成"能答"。
> 我刻意没上 ReAct——我们的问题九成是单跳，多步推理的收益抵不过延迟和可审计性的代价。
