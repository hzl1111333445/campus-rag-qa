# 校园规章 RAG 问答系统 · 项目是怎么做出来的

> 这份文档回答一个问题：**从零到"能演示、能投简历"，这个项目是怎么一步步做出来的。**
>
> 素材来源：`docs/00-完整工作日志.md`（全过程）、`docs/04-工作日志.md`（逐次施工记录，约 12 万字）、`docs/17-RAG阶段总结.md`（检索与生成链路定稿）、`docs/15-端到端回答评测.md`、`docs/16-两段式生成.md`、`docs/19-项目讲解与自测.md`。
>
> 写法原则：每个阶段只写四件事——**要解决什么问题 / 试了什么 / 数据是多少 / 学到什么**。失败和反悔照实写，那些才是这份文档里最值钱的部分。

## 0. 一句话与一屏数字

**它是什么**：学生用大白话问校园规章制度（旷课怎么处分、宿舍几点关门、转专业几次），系统给出**带原文出处的答案**，答不了就说"本知识库暂未收录"。

**最终形态**：Spring Boot 3.5 + JDK 21 后端（47 个类 / 5367 行）+ Vue 3 前端（7 个页面 / 2485 行）+ MySQL，打成**单 jar 71.7 MB**，一条 `java -jar` 跑起整个系统。

| 维度 | 数字 |
|---|---|
| 语料 | **33 份**规章 / **643 块** / 约 **24 万字**（含 11 份扫描件 OCR） |
| 评测题集 | **120 题**（118 应答题 + 2 无答案题），dev 62 / test 56，含 30 道硬改写 |
| 检索效果 | Recall@3 **90.68%**、MRR **0.8531**（纯向量 75.42% 起） |
| 端到端效果 | 严格正确 **51.7%**、含部分正确 **78.8%**、幻觉 **34.7%**（基线 48.3%）、误拒 **5.1%**（基线 7.6%） |
| 性能 | 完整回答 1.4s 均值；流式首字 1.0~1.9s；检索层拒答 0.44s |
| 规模 | 接口 **30 个**、数据表 **5 张**、单测 **5 类**、文档 **20+ 篇**、提交 **50+ 次** |

## 1. 起步：先把"能不能做"判断清楚（11-05）

### 要解决的问题
毕业设计选题定了方向——「基于 Spring Boot + RAG 的校园智能问答系统」，但它到底是"能做的题目"还是"调包 demo"，必须先判断。

### 当时说清的三件事
1. **选题可行且优质，但贡献必须落在切分 / 检索 / 重排 / 引用 / 量化评估上**，否则就是一个"把文档喂给大模型"的玩具。
2. **JDK 8 跑不了 Spring Boot 3**（要求 17+），这是硬门槛——先解决环境，再谈功能。
3. **不能拿 Python + LangChain + Chroma 当主栈**，题目写的是 Spring Boot，主栈必须是 Java。

### 环境落地（后面全程复用）

| 项 | 结果 |
|---|---|
| JDK | Temurin **21.0.13** → `E:\cal\code\jdk21`（原 JDK 8 保留不动） |
| Maven | 3.9.14 |
| MySQL | 8.0.43 |
| Node / Python | 24.14.0 / 3.13.9 |

**教训**：环境问题的表现经常和原因离得很远。`类文件具有错误的版本 55.0` 报的是"编译错"，真正原因是 Maven 跑在 JDK 8 上。做法是**每次命令都显式指定 `JAVA_HOME`**，不要指望继承的环境变量。

## 2. 技术验证：在写系统之前，先单独验证每个技术点（11-05）

### 要解决的问题
RAG 有 6 个环节（解析、切分、向量化、检索、融合、生成），如果在系统里一起调，出错时根本分不清哪一环的问题。所以先做实验室（labs）。

### 做了什么
| 实验 | 内容 | 结果 |
|---|---|---|
| Python 版 RAG | 纯标准库 200 行，哈希向量 512 维 | 5 道题 Top-3 命中 **4/5**；切成 150/30 掉到 3/5 |
| Java 版 RAG | Chunk / TextSplitter / BM25 / RRF / 手写向量 | 向量 4/5、**BM25 5/5**、混合 5/5 |
| 文档解析 | Tika 3.3.3 解 9 种文件 | docx、正常 PDF、txt 都能读；**扫描件 PDF 0 字**；缺 ToUnicode 的 PDF 只有 15 字碎片 |

### 三个真发现（直接决定了后面两个月的活）
1. **扫描件 PDF 必须 OCR**——学校发的规章里有 11 份是扫描件，Tika 一个字都提不出来。
2. **缺 ToUnicode 映射的 PDF**：人看得见、机器抠不出，只能拿到 ASCII 碎片。
3. **docx 表格能提取但列关系丢失**：`10-19 学时 警告 由学院处理` 被压成一行，语义全乱。

### 教训
**先验证再集成**。这半天花的成本，换掉了后面"系统调不通却不知道哪错"的无底洞。

## 3. 第一次翻车：我替他建了一整套系统（11-18）

这一段是整个过程里最贵的一课。

### 发生了什么
我在 `E:\tmp\ai` 里按"教学仓库"的方式，把 RAG 全套都写了一遍：后端链路、SSE、会话记忆、混合检索、精排三级降级、评测接口，前端五个面板，还配了 70 题评测。技术上跑得通，但用户的原话是：

> 「你先别急着答辩啊循序渐进懂吗，**你在开飞机吗**」
> 「你是不是应该给点注释和讲解呢，这样我感觉**我一直在复制粘贴**」
> 「**你不能闷头写啊那我呢**」

### 根因
**我建得越多，他越像旁观者。** 项目成了"我的"，不是"他的"。简历上写"个人项目"，但他讲不清里面的任何一步。

### 处置
推倒重来。新的施工地点是用户自己在 IDEA 里建的 `E:\tmp\campus-ai-rag\demo`（Spring Boot 3.5.16 + JDK 21），并约定三条：

1. **先讲后写**：每步先用 5 行说清解决什么问题、为什么这么拆
2. **留 2~3 处 TODO 让他自己填**，填完我再 review
3. **他自己跑命令、看日志、贴报错**，我只负责解读

**教训**：教别人做项目，交付物不是"能跑的代码"，而是"他能讲清的代码"。这两者的距离，等于重做一遍。

## 4. 重建：一条链路一步一步跑通（11-18 晚 → 11-21）

### 施工顺序与证据
| 步骤 | 产出 | 证据 |
|---|---|---|
| 1. 骨架 + 健康检查 | `CampusRagApplication`、`HealthController` | `GET /api/health` 返回 `javaVersion: 21.0.13` |
| 2. 上传存盘 | `DocumentStorage`（UUID 命名，防重名 + 防 `../` 穿越） | 308,804 字节 PDF 存盘成功 |
| 3. 入库 | `DocumentDao`（JdbcTemplate + KeyHolder）、`kb_document` | `id=1` 写入，中文正确 |
| 4. 解析 | `DocumentParser`（Tika 3.3.3） | 12 份真实 PDF：6 份能读、**11 份扫描件 0 字** |
| 5. 切分 | `TextSplitter` + 单测 4 例 | 587 字样例 → 9 块，测试全绿 |
| 6. **修切分** | 删换行 / `minChunk = size*0.65` / <10 字并入前块 | 块数 **748 → 305**，平均块长 **99 → 195**，最短 1 → 132 |
| 7. 向量化 | bge-m3 / 1024 维，JSON 存 MySQL | 295 条 / 19 批 / **6.1 秒** |
| 8. 检索 | 点积 + TopK + BM25 + RRF | 189 块，单查询 167~658ms |
| 9. 生成 | `ChatClient` + `PromptBuilder` + `QaService` | DeepSeek 真调用，786~1563ms |

### 这一段的三个坑（都值得记）
1. **切分平均只有 100 字（目标 220）**：三个原因叠加——①PDF 换行被当成句子边界；②"回退到句末 + 重叠"双重缩短；③出现 1 字碎片。修完块数从 748 降到 305，块长翻倍。
   → **这条是"用数据定位问题"的第一个范例**：不是感觉切得碎，是把块长分布打出来，看见"平均 99、最短 1"。
2. **Embedding 返回的 `data[]` 顺序不保证**：必须按 `index` 字段排序，否则向量和文本错位，检索全乱。
3. **换模型 / 换切分参数后旧向量静默失效**：后来加了 `config_hash = sha256(模型 + 维度 + 切分参数)` 做指纹校验，不匹配直接报"需要重新导入"，而不是默默给出错误结果。

## 5. 检索定稿：从 75% 做到 90.68%（11-22）

### 要解决的问题
"能不能答对"的前提是"能不能捞到正确的块"。所以先把检索这条路走到底。

### 做法：每一步都单独量化
| 改动 | 做了什么 | 净收益 |
|---|---|---|
| 双路召回 | 手写 BM25（bigram，K1=1.5/B=0.75）+ 向量余弦，两路各取 TopN | 混合 vs 单路 **+3~5pt** |
| RRF 融合 | `score = Σ 1/(60 + rank)`，两路加权 0.2 / 0.8 | 让两路"错的地方不同"互相补 |
| 相邻块去重 | 同一文档相邻块只留分数最高的 | 减少重复占位 |
| **精排** | bge-reranker-v2-m3 Cross-Encoder，Top10 → Top3 | **+5~7pt**，且可用性有三级降级（不可用就退回 RRF 顺序，接口不中断） |
| **展开邻居** | "排序用单块、给模型看用三块" | MRR **+0.03~0.05**，零额外成本 |
| 查询改写 | 信号 <1.5 才触发（省调用） | 硬改写 70% → 76.7% |
| 双查询融合 | 原句 + 改写句两路各自检索再融合 | 总 89.83% → **90.68%** |

### 13 种配置的横向对比（118 应答题 × 643 块）
| 配置 | Recall@3 | MRR |
|---|---|---|
| 纯向量 | 75.42% | 0.6271 |
| 纯 BM25 | 77.12% | 0.6822 |
| 混合 RRF | 80.51% | 0.7274 |
| 混合 + 精排 | 82.20% | 0.7500 |
| 合并相邻块 + 精排 | 88.14% | 0.8192 |
| 精排 + 展开邻居 | 89.83% | 0.8333 |
| **双查询融合 + 精排 + 展开（线上）** | **90.68%** | **0.8531** |

### 三个诚实结论
1. **检索已接近上限**：46 道答不好的题里只有 16 道与检索有关（后经分类确认：**65% 是"资料已在 Top3、模型还编"**）。
2. **硬改写是真短板**：口语问法 Recall@3 只有 76.7%（问"寝室能通宵打游戏吗"，原文写的是"作息""熄灯"）。这不是调参能修的，要 doc2query / 术语表。
3. **关键词命中 ≠ 答案完整**：现有 Recall 口径偏宽（"块里出现全部关键词"就算命中），没测"证据覆盖率"。这条必须写进论文局限。

## 6. 生成层与端到端评测：第一次把"答得好不好"量出来（11-22 夜）

### 要解决的问题
检索 90.68%，但用户看到的是答案。**检索好 ≠ 答得好**，中间还隔着模型。

### 做法：三件套
1. **120 题评测集**（118 应答题 + 2 无答案题，dev 62 / test 56，含 30 道硬改写）
2. **跑完整链路**：120 题逐题打 `/api/qa`，落原始 TSV
3. **DeepSeek 当裁判**：给"问题 + 标准要点 + 检索到的资料原文 + 系统输出"，判 5 档 + 幻觉标记
4. **人工抽查**校准裁判口径（裁判有抖动，同一题跨版本判分不一致，±2~3 道不可信——这条也写进局限）

### 三版对照（118 应答题）
| 版本 | 严格正确 | 含部分正确 | 幻觉 | 误拒 | 延迟 |
|---|---|---|---|---|---|
| 基线 | 48.3% | 80.5% | 48.3% | 7.6% | 1.39s |
| 提示词硬化（8 条规则） | 52.5% | 76.3% | 33.1% | 10.2% | 1.17s |
| **硬化 + 阈值 0.015** | **51.7%** | **78.8%** | **34.7%** | **5.1%** | 1.39s |

### 关键洞察：42 个点丢在哪
| 环节 | 损耗 |
|---|---|
| 检索没给到 | 9.3pt |
| **有资料但加料（部分正确）** | **32.2pt** |
| 误拒 | 5.1pt |
| 真错 | 5.1pt |

一句话：**主要矛盾不在检索，在"模型对着资料还自己加细节"。**

### 于是做了 badcase 四分类（46 道答不好的题逐题归因）
方法：把 643 块全导出，算"同时包含全部关键词的块数"，再用 Top10 检索看正确块排第几。

| 类别 | 含义 | 数量 |
|---|---|---|
| **D 生成层** | 正确资料已在 Top3，模型还是答错 | **30 道（65%）** |
| A2 召回不到 | 库里有，Top10 都没捞到 | 10 道（22%） |
| A 排序偏了 | 库里有，排在 4~10 | 6 道（13%） |
| BC 语料缺失 | 库里根本没有 | **0 道** |

**这一步推翻了三个之前拍脑袋的判断**：
1. 不是"缺知识"（BC = 0），所以"把模型已知内容写进向量库"这个想法被否决——那会造成循环自证。
2. 上下文补全只值 6 道，不是原先估的 15~20 道。
3. 主战场是生成层，所以后续优先级整体改写：**两段式 / 证据宽度 > 展开宽度 > doc2query**。

## 7. 四个被自己的数据否掉的方案（负结果）

这一段是整份文档里最该被论文和面试引用的部分：**能说出"什么没做成、为什么"，比列出"做了什么"更有说服力。**

| 实验 | 预期 | 实际 | 处置 |
|---|---|---|---|
| **自适应融合权重**（BM25 信号弱就加大向量权重） | 硬改写 +10pt | 只多对 1~2 道，dev 集零变化 | 默认关闭，只留接口 |
| **两段式生成**（先摘原句 JSON，核验后再组答案） | 严格正确 +10pt | 幻觉 −3.3pt，但误拒 +4.2pt，正确率持平，延迟 1.39→2.05~2.40s | 默认关闭，留开关 |
| 双查询融合权重误用 0.2（借了向量权重） | — | 结果与纯混合完全相同 = **白测一次** | 改成独立配置 `fusion-w-rewritten: 0.5` |
| "把模型答对的内容写进向量库" | 提升召回 | badcase 分类显示库内零缺失，**没有需求** | 否决 |

**教训**：
1. **小样本会出假阳性**。46 题时"重排有用"，扩到 70 题后反转成"重排有害"——因为重排靠字面覆盖率，而改写型题最怕字面不一致。
2. **负结果必须记录**。它证明你不是在"堆功能"，而是在"用数据做决定"。
3. **参数要独立**。借错一个权重（0.2 是向量权重），整轮实验白做。

## 8. 工程化：从"能跑"到"能交付"（11-22 深夜 → 11-23）

RAG 链路定稿后，工作重心转向"用户看得见、要用的东西"。这一段修出了几个**真缺陷**，每个都值得单独讲。

### 8.1 前端五个页面
| 页面 | 关键点 |
|---|---|
| 智能问答 | 对话式气泡、SSE 流式吐字、引用卡片可展开、三个诚实性标签（引用校验 / 接地校验 / 未引用资料） |
| 文档管理 | 上传后自动解析→切分→**向量化**、看块抽屉（能看到"块头带【文档·章节】"）、重处理、删除 |
| 检索调试 | **五路召回并排对比**（纯向量 / BM25 / 混合 / 混合+精排 / 精排+展开），标出"哪条命中了线上最终结果" |
| 评测看板 | 点一下跑 13 种配置，进度条 + 结果表 + 按题型/按 dev-test 拆解 + 未命中题下钻 |
| 环境自检 | 服务、库、向量、接口、题集五项体检 |

### 8.2 五个"真缺陷"（都是自测时发现的）
| 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **上传文档不向量化** | 传完搜不到，只有 BM25 能命中 | 入库只做解析→切分→写块，向量化是单独接口 | upload 与 reprocess 成功后自动补该文档的向量；页面加"向量化"列和行内按钮 |
| **密码错返回 500** | 输错密码得到"服务器错误" | 业务异常没映射状态码 | 加 `AuthException` + `GlobalExceptionHandler`，返回 401 |
| **评测污染对话库** | 管理员看到一屏同名"匿名会话" | 评测脚本每跑一次写 118 条会话 | 加 `X-No-Persist` 头（机器调用旁路），并清理 162 条垃圾数据 |
| **citationOk 语义错** | 拒答回答被标"引用编号异常" | `invalid.isEmpty() && !cited.isEmpty()`，把"没引用"当"引用错" | 改成 `invalid.isEmpty()`，前端三态显示 |
| **抽屉撑破屏幕** | 长中文把抽屉拉宽 | flex 子项默认 `min-width: auto` | `min-width: 0` + `overflow-wrap: anywhere` |

**教训**：
- **"入库 ≠ 可用"**：写进数据库只是第一步，能检索到才算完成。
- **默认异常一律 500**，业务语义必须显式映射状态码。
- **机器调用和真人调用要分开**：给机器留显式旁路，比事后清数据可靠。

### 8.3 安全与多用户（11-23）
| 能力 | 做法 | 关键取舍 |
|---|---|---|
| 登录与角色 | 手写 HMAC-SHA256 令牌（不引第三方库），管理员 / 学生两种角色 | 令牌放 `Authorization: Bearer`；`sha256(salt+密码)` 并注明生产应换 BCrypt |
| 权限拦截 | `AuthInterceptor` 先"识别身份"，再按前缀拦 `/api/document`、`/api/dev`、`/api/eval` | 解析失败不拦（公开接口照常），需要登录的才拦 |
| **数据隔离** | `qa_session.user_id` + 纯函数 `SessionAccess.can()` | **越权返回"不存在"（400）而不是 403**——403 会泄露资源存在性 |
| 机器旁路 | `X-No-Persist: 1` | 评测 / 压测不建会话、不写消息 |

### 8.4 多轮上下文（两小步）
| 步骤 | 做了什么 | 结果 |
|---|---|---|
| 第 1 步：历史进生成层 | `ContextAssembler`：最近 3 轮、单条截断 120 字、总量超 600 字整条丢；**抹掉历史里的 `[n]` 编号** | 追问「那留校察看呢」能答出 12 个月与解除条件 |
| 第 2 步：历史进检索层 | 追问补全：分数 < 0.30 才触发，补全后重新检索，**只有分数更高才采用** | 8 组追问 Top1 正确率 **单轮 3/8 → 带历史 8/8** |

**关键认知**：**"聊天框套单轮"和多轮 RAG 的分界线是——历史有没有进检索层。** 只塞进 prompt 里，遇到省略式追问照样检不到正确资料。

### 8.5 流式输出
- 后端新增 `/api/qa/stream`（`SseEmitter` + **独立线程池 8**，否则长连接会吃光 Tomcat 工作线程）
- 事件顺序 `meta → sources → token → done`：先告诉用户"查到了哪几条"，再逐字给答案
- 首字 **1.0~1.9s**，其中检索占 1.0~1.4s —— 所以诚实的说法是"检索完成后逐字出现"，不是"秒出"

## 10. 沉淀下来的方法（比代码更值钱）

### 10.1 技术方法（10 条）
1. 切分要按**句子边界**回退，且回退要有下限（`size*0.65`），否则"回退 + 重叠"双重缩短把块切碎。
2. **PDF 的换行不是句子边界**，必须先删掉再切。
3. 切完要**过滤 / 合并超短块**（<10 字），否则污染检索。
4. Embedding 返回的 `data[]` **顺序不保证**，必须按 `index` 排序。
5. 向量必须**统一归一化**，点积才等于余弦。
6. 换模型 / 切分参数后旧向量会**静默失效** → 存 `config_hash` 做指纹。
7. 纯向量对**列举型 / 数字型**弱，BM25 补位；融合要**按路加权**。
8. **靠字面覆盖率的重排对改写型是负收益**（46→70 题时被数据反转）。
9. 扫描件必须 OCR；缺 ToUnicode 的 PDF 人看得见、机器抠不出。
10. 幻觉只能"**降低 + 可发现**"，校验要从"编号越界"升级到"内容溯源"。

### 10.2 工作方法（8 条，这一份更通用）
1. **先跑通再优化**：一条链路能端到端跑，比五个环节各自完美有用。
2. **每步留数据**：没有数字的改动等于没做；"感觉变好了"不是结论。
3. **小样本会骗人**：46 题时的结论，70 题就被推翻。
4. **拆 dev / test**：只看 dev 会高估自己（曾出现 9pt 差距）。
5. **先定位再优化**：badcase 四分类之前，猜"缺语料 / 缺上下文"全错。
6. **主动记录负结果**：4 个被否掉的方案，是最能证明判断力的材料。
7. **机器调用与真人调用分开**：评测旁路、批量接口都要能"不落业务数据"。
8. **加而不改**：新能力（`X-Session-Id`、`X-No-Persist`）尽量用"新增"实现，别动老接口，否则评测脚本和外部调用全要跟着改。

### 10.3 一条教训（代价最大的）
> **教别人做项目，交付物不是"能跑的代码"，而是"他能讲清的代码"。**

第一版替用户把所有东西写完，技术上没问题，但用户讲不清任何一步——于是只能推倒重来。后来的做法是：先讲 5 行原理、留 2~3 处 TODO 让他填、他自己跑命令贴报错。
