# 32 · Agent 分流评测：该查的查了没有

> 目标：量"该检索却直接作答"（漏检）与"不该检索却查了"（多查）。
> 这不是正确率评测，只测**决策**——答得对不对由另外两套评测负责（`docs/15`、`docs/25`）。

## 1. 为什么要单独评测分流

删掉"第 1 步必须检索"这条铁律之后，系统获得了一个新能力，也获得了一个新风险：

- 能力：闲聊/概念/学习建议这类问题能直接回答（以前 100% 被拒答）
- 风险：模型可能"偷懒不查"，把校内具体规定凭印象说出来 —— 这正是我们花两个月压幻觉最不想看到的

**所以这个开关能不能默认打开，不取决于它让对话变自然，而取决于漏检率。**

## 2. 题集与口径

- 题集：`data/testset/agent_routing_questions.tsv`，20 题
  - 该检索 10 题：旷课处分 / 转专业次数 / 助学金金额 / 门禁时间 / 作弊处理 / 助学贷款材料 / 学位条件 / 请假审批 / 电器功率 / 重修费用
  - 不该检索 10 题：身份 / RAG 概念 / 学 Java / 自我介绍 / 向量库对比 / 二叉搜索树 / 你好 / 谢谢 / 语言选型 / 讲笑话
- 判定"是否真的检索"：`steps > 1` 或 `allowedChunks` 非空
  - 直接作答：1 步就 final，chunks = 0
  - 检索后作答：第 1 步 `search_rules` → 第 2 步 final，steps ≥ 2
- 脚本：`tools/eval-agent-routing.py`；原始结果 `docs/eval-runs/agent_routing_2026-11-25.tsv`

## 4. 两条发现

### 4.1 「多查」那例其实是合理多查，不是错误

`#14 帮我想个自我介绍` 走了 3 步、检索 3 块、6.9s，但最终答案是：

> 以下不是校内规定，仅供参考。**检索了校内规章，没有找到关于「自我介绍」的具体规定**，所以按通用写作建议给你：…

它先怀疑自己（"自我介绍要不要引用学校规定？"）→ 查了 → 确认没有 → 转通用并**说清楚为什么转**。
代价是 ¥0.0103 与 3.7 秒，换来的是"不假装懂校内规定"。**这类多查应该保留，不该优化掉。**

### 4.2 闲聊的延迟下限不是 0

`你好` 1.1s、`谢谢` 1.2s —— 已经是一次完整模型调用（1 步）。也就是说：**放开闸门后，任何闲聊都要花一次调用**。
比 `/api/qa` 的 1.6s 慢的地方不在闲聊，而在多步：该检索的题平均 3.7s（2~3 步各一次调用）。

## 5. 局限（必须写清）

1. **20 题是我出的**，按"典型问法"设计，不含口音化/脏输入（无标点三连问、两字提问），真实漏检率可能更高
2. 没测**多轮**：带历史时模型是否更容易"沿用上一轮证据"而不检索，未验证
3. 没测**边界问法**：如"我这种情况会不会被处分"（口语 + 隐含条件），既可能漏检也可能多查
4. 判定用 `steps>1 || chunks>0`，如果模型检索到 0 块后直接答（库里确实没有），会被算作"已检索"——统计上偏宽松

## 6. 下一步

- 扩到 50 题，其中 20 题是脏输入（口语/省略/错别字），重点看漏检
- 加多轮场景（同一会话第 3 轮问一个不相关新问题，看它是否误用旧证据）
- 若漏检率仍 < 5%，可以把 Agent 入口设为前端默认；否则加"检索前置规则"兜底

## 8. 结论与建议

1. **漏检 30/30 全部正确** → 这个开关可以默认打开（`campus.agent.enabled=true`）
2. 唯一的"多查"是模型主动核对（查完明说没找到再转通用），代价 ¥0.01，**保留**
3. 剩余风险不在分流，在**多轮**：带历史时模型可能沿用上一轮证据而不重新检索，这一点 v2 仍未覆盖
4. 延迟仍偏高（平均 3.2s，闲聊也要 1.1~1.5s），下一步优化点是"闲聊走轻量模型"或"短问句跳过循环"

## 9. v3：多轮分流（补 v2 最后一个盲区）

v2 只测单轮。多轮的风险是另一件事：**模型可能把上一轮查到的证据当成本轮依据**，于是"引用看着合法、其实答的是上一个问题"。

### 9.1 先补上 Agent 的多轮能力

原实现里 `AgentLoop` 只把 `system + question` 发给模型，**根本没有历史**。这次接上：

- `AgentController` 负责解析/新建会话（`sessionDao.create`）、`contextAssembler.load()` 取历史、结束后落库 user + assistant 两条
- `AgentLoop` 把历史包成一段 `<history note="只用于理解指代，不能作为事实依据；本轮结论必须靠本轮工具返回的证据">…</history>`，放在 question 之前
- 关键约束写在 note 里：**历史不是证据**。否则引用校验（`badCitations` 对着本轮 `allowedChunks` 算）会失去意义

### 9.2 实测（原始输出）

**场景 1：校内 → 闲聊 → 校内（完全不同主题）**

| 轮次 | 问题 | 是否检索 | 步数 | 块数 | 耗时 |
|---|---|---|---|---|---|
| 1 | 旷课多少学时会被处分？ | 查 | 2 | 5 | 3683ms |
| 2 | 你是谁 | **没查** | 1 | 0 | 985ms |
| 3 | 图书馆借书能借多久？ | **重查** | 2 | 5 | 4233ms |

第 3 轮的 `allowedChunks = [1729, 1731, 1701, 1715, 1725]` —— 全部是《图书借阅规则》的块，**没有一块来自第 1 轮的考勤制度**。答案引用 `[1][2]` 均为图书馆规则。→ 没有沿用旧证据。

**场景 2：校内 → 追问（应当理解指代、但证据要重取）**

| 轮次 | 问题 | 是否检索 | 步数 | 块数 | 耗时 |
|---|---|---|---|---|---|
| 1 | 国家助学金一年多少钱？ | 查 | 2 | 5 | 1959ms |
| 2 | 那要怎么申请？ | **重查** | 3 | 6 | 5191ms |

第 2 轮基于历史把"那"解成"国家助学金"，重新检索后引用了《国家奖助学金实施办法》第十条（申请时间为 9—10 月）。→ 指代理解正确，证据独立。

### 9.3 结论

- 多轮下"闲聊不查、新主题重查、追问重查"三种行为都正确
- 剩下的是代价：追问那一轮用了 3 步 5.2s（比单轮 2 步慢一倍），因为每步都调一次模型
- 待办：把"多轮 + 脏输入"交叉起来测（第 2 轮故意问一个省略式的新主题），以及给 `AgentLoop` 补单测（预算/窗口/历史隔离三条）
