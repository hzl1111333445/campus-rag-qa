## 1. 我们要做的系统，一句话

> 学生在网页上问一句"我能转专业吗"，系统去学校现行的 20 份规章制度里找出相关段落，交给大模型组织成回答，并标出"这句话出自《本科生转专业管理办法（2026年修订）》第五条"。

它内部有两条链路，一慢一快：

```
【入库链路】离线跑一次，把文件变成能搜索的数据
  PDF/Word  →  解析成文字  →  切成小块  →  每块算成一个向量  →  存进数据库

【问答链路】用户每问一次，跑一次
  用户问题  →  问题也算成向量  →  在数据库里找最像的几块  →  拼成提示词  →  大模型回答  →  标出处
```

两条链路共用一个东西：**向量**（第 5 章）。整本书的核心就是它。

## 2. 为什么需要 RAG？不能直接问大模型吗？

因为大模型**不知道你们学校的规章**。

大模型的知识来自它训练时读过的公开文本。它可能知道"中国大学一般允许转专业"，但它不知道你们学校规定"平均学分绩点不低于 3.0、且在校学习满一学年才能申请"。

它有四个硬伤：

| 硬伤 | 具体表现 |
|---|---|
| 不知道私有知识 | 你们学校的文件没有公开到网上，它没读过 |
| 知识有截止时间 | 训练数据只到某个时间点，2026 年新修订的办法它不知道 |
| 会编（幻觉） | 不知道也照样自信地回答，编出"根据我校规定第三条……" |
| 无法给出处 | 说不清这句话从哪来，用户没法核实 |

三种解决思路对比：

| 做法 | 缺点 |
|---|---|
| 微调模型（把规章喂进去重新训练） | 贵、慢、每改一版文件就要重训；仍然会编 |
| 把所有规章塞进提示词 | 20 份文件几十万字，超长、每次请求都很贵、还很慢 |
| **RAG（先检索，只把最相关的几段给模型）** | 需要自己搭检索，但便宜、文件改了立刻生效、**能标出处** |

RAG = Retrieval Augmented Generation，检索增强生成。名字很唬人，意思就是：**先去资料里查，再让模型照着资料说**。

## 3. Spring Boot 在我们系统里干什么

先把两个词分开：

- **RAG 是业务逻辑**：怎么切、怎么算向量、怎么检索、怎么让模型引用。
- **Spring Boot 是脚手架**：让你的 Java 代码能对外提供网页接口、能连数据库、能读配置。

用开餐厅打比方：

| 餐厅里的角色 | 对应代码 | 干什么 |
|---|---|---|
| 服务员 | `Controller` | 接待客人（HTTP 请求），把菜端回去（JSON 响应） |
| 厨师 | `Service` | 真正干活的：解析、切分、检索、调模型 |
| 库房管理员 | `Dao` / `Repository` | 只负责和数据库打交道（存、查） |
| 菜单和价目表 | `application.yml` | 配置：端口、数据库地址、切分参数 |

**Spring Boot 替你干掉了这些脏活：**

1. 启动 Web 服务器（内置 Tomcat）——不用你自己写 `main` 里一堆启动代码
2. 把 Java 对象自动转成 JSON——不用手写字符串拼接
3. 管理数据库连接池——不用每次查询都 `DriverManager.getConnection()`
4. 读配置——`@Value("${campus.upload-dir}")` 就把 yml 里的值注进变量
5. **依赖注入**：你需要哪个对象，声明在构造器里，它自动 new 好给你

最后这条是 Spring 的灵魂，叫 **IoC / 依赖注入**。你现在已经在用它了：

```java
public DocumentController(DocumentStorage storage, DocumentDao documentDao) { ... }
```

你没写 `new DocumentStorage()`，Spring 看你要，就把它造好塞进来。好处：换实现（比如把存磁盘换成存阿里云 OSS）只改一个地方。

**一句话记住两者的关系**：Spring Boot 负责"怎么把功能暴露出去、怎么连数据库"，RAG 负责"功能本身怎么算"。

## 4. RAG 的六个环节

### 入库链路（离线，文件变了才跑）

#### ① 解析：从文件里把文字抠出来

PDF/Word 里存的不是字，是"在坐标 (x,y) 画这个字形"的排版指令。要得到文字必须用解析库，我们用 **Apache Tika**。

**坑**：扫描件 PDF（拍的照片/扫描的纸）没有文字层，只能得到 0 个字符，必须走 **OCR**（图像识别文字）。我们下载的 20 份文件里有 12 份是扫描件。

#### ② 切分：把长文切成 200 字左右的小块

为什么必须切：

- 模型有输入长度上限，整份文件塞不进去
- 就算塞得进去，塞 20 份文件每问一次都极贵
- 检索的粒度越细，答案越精准

为什么要**重叠**（每块和上一块重复几十字）：

- 一句话可能刚好被切在中间，两半都不完整
- 重叠能让关键的上下文至少在一块里是完整的

**块大小和重叠这两个数，就是你论文里要做对比实验的变量。** 切太大：一块里混了多个主题，检索不准；切太小：一句完整的规定被切散，模型看不懂。

#### ③ 向量化 + 入库

把每一块文字变成一串数字（一个"向量"），和原文一起存进数据库。见第 5 章。

### 问答链路（在线，每次提问都跑）

#### ④ 检索：找出最相关的几块

用户的问题也变成一个向量，然后到数据库里找"向量最接近"的几块。通常取前 3~5 块。

两种检索方式各有短板，所以我们**两个都用**（第 6 章）：

- 向量检索：懂"意思相近"（宿舍 ≈ 公寓），但对精确数字不敏感
- 关键词检索（BM25）：对"3.0""23:00""60 学时"很准，但不认识同义词

#### ⑤ 组装提示词：把资料和问题包成一段话

把检索到的几块原文，加上系统规则，拼成这样：

```
【系统规则】只根据下面资料回答；资料里没有就说"资料中没有找到相关规定"；
每条结论后面用 [1][2] 标注来自第几段资料。

【资料】
[1]《学生学籍管理规定》第五条：……平均学分绩点不低于 3.0……
[2]《本科生转专业管理办法》第三条：……

【用户问题】我能转专业吗
```

#### ⑥ 生成 + 引用校验

大模型按资料回答，并在句末写 `[1]`。**关键一步**：回答返回后，后端要检查这些编号是否真实存在（防止模型编出 `[7]`，而实际只给了 3 段资料）。这一步叫**引用校验**，是防幻觉的最后一道闸。

## 4.5 我们到底用了哪些算法（总表）

第 5~8 章会逐个展开。这里先给一张"地图"：一共 **4 个算法 + 1 个大模型**，各管一段。

| 环节 | 用的东西 | 一句话解释 | 代码在哪 | 谁提供的 |
|---|---|---|---|---|
| 切块 | 滑动窗口 + 句末回退 | 220 字一刀，但尽量切在句号处；相邻块重叠 50 字 | `TextSplitter` | 我们手写 |
| 检索路 1 | **余弦相似度（点积）** | 问题和块都变成 1024 维向量，比方向是否一致 | `RetrievalService` | 我们手写（向量由 bge-m3 生成） |
| 检索路 2 | **BM25** | 看字面：词越稀有越值钱，块越短越加分 | `Bm25Index` | 我们手写 |
| 融合 | **RRF（倒数排名融合）** | 两路各排一次名，按名次给分相加 | `RetrievalService.rrf()` | 我们手写 |
| 精排 | **Cross-Encoder**（bge-reranker-v2-m3） | 问题和块拼一起送模型，判断"这段答不答得上" | `RerankClient` | 调硅基流动接口 |
| 生成 | DeepSeek + 提示词 | 把前 3 块当资料，只依据资料回答并标 `[n]` | `ChatClient` / `PromptBuilder` | 调 DeepSeek 接口 |
| 评测 | **Recall@K / MRR** | 正确答案有没有进前 3？排第几？ | `EvalService` | 我们手写 |

### 为什么"算法"要分两类

- **检索算法**（余弦 / BM25 / RRF / Cross-Encoder）：负责"找出哪几块资料相关"
- **生成模型**（DeepSeek）：负责"把资料写成一句人话"

很多人以为 RAG 的重点是后者。其实**资料找错了，再强的模型也只能编**——这就是我们花了整整一轮在检索评测上的原因。

### 用「国家奖学金一年多少钱」走一遍（带真实数字）

```
问题 ──► 变成 1024 个数字（bge-m3）
          │
          ├─ 路1 余弦：414 个块逐个比 → 排名
          └─ 路2 BM25：414 个块逐个算字面分 → 排名
                     ↓
          RRF 融合：两块都排前面的，融合后更靠前
                     ↓
          取前 10 条候选
                     ↓
          精排：10 条各自和问题拼一起，模型打分
                 含「10000 元」那块 → 0.6521   ← 顶到第 1
                 讲评审程序那块   → 0.3003
                     ↓
          取前 3 条 → 喂给 DeepSeek → 答案 + [1][2] 引用
```

⚠️ **别拿两路的分数互相比**：RRF 分是"名次分"（约 0.016 量级），精排分是"相关性分"（0~1）。
拿它俩比大小，等于拿菜和盐比咸淡——**只有同一路内部的名次/分数可比**。

### 这张表就是面试答案

面试官问"你这个 RAG 怎么做的"，可以这样答：

> "检索我手写了 BM25 和向量两路，用 RRF 融合，再用 Cross-Encoder 精排。
> 在自建的 36 题（32 道有效）题集上，Recall@3 从 0.9375 提到 0.9688，MRR 从 0.875 提到 0.9063。"

比说"我用了 LangChain"强得多——因为每个数字你都能解释来源。

## 5. 向量（embedding）到底是个啥

### 一句话

**向量 = 把一段文字变成一串数字，意思越接近的两段文字，它们的数字串在数学上越"近"。**

比如（示意，真实是 1024 个数字）：

```
"宿舍"     → [0.21, -0.03, 0.88, ...]
"公寓"     → [0.19, -0.01, 0.85, ...]   ← 很接近
"奖学金"   → [-0.7, 0.42, 0.11, ...]    ← 离上面两个很远
```

### 怎么衡量"近"

把这些数字当成一个空间里的坐标（1024 维空间的点），两个点越近越相似。工程上一般算**余弦相似度**：看两个向量箭头的夹角，夹角越小越像。

### 为什么它能懂同义词

因为生成向量的模型（叫 **embedding 模型**）是在海量文本上训练出来的，它见过"宿舍"和"公寓"经常出现在相似上下文里，于是把它们放在了相近的位置。

### 一个必须知道的限制

**向量好不好，全靠 embedding 模型。** 我们开发阶段为了不花钱、不需要 API Key，用一个"哈希假向量"顶着（把文字按字面摊成数字）——它能跑通流程，但**不懂语义**：问"宿舍"匹配不到"公寓"。

这就是为什么我在我的参考版本里，用假向量跑出来的评测是"关键词检索碾压向量检索"——那组数字**不能写进简历/论文**。换成真模型（如 `BAAI/bge-m3`）后结论会反转。这也是你论文里一个天然的对比实验：假向量 vs 真向量。

## 6. 关键词检索（BM25）为什么还要留着

BM25 是老牌搜索引擎算法（BM 是 Best Matching 的缩写，25 是它第 25 版公式）。它的思路很朴素：

> 一个词在这段文字里出现得越多、在整个资料库里越少见，这段文字就越可能和这个词相关。

为什么有了向量还要它？因为两者的短板正好互补：

| | 向量检索懂什么 | 关键词检索懂什么 |
|---|---|---|
| 同义词 / 换个说法 | ✅ 宿舍 ≈ 公寓 | ❌ 字不一样就找不到 |
| 精确数字 / 专有名词 | ❌ 对"23:00"不敏感 | ✅ 出现就是出现 |
| "转专业要多少绩点" | 语义能对上 | 关键词也对得上 |

所以现代 RAG 系统基本都是**混合检索**：两路各查一遍，再把结果融合。

### 融合（RRF）怎么融

不能直接把两边的分数加起来——向量的余弦是 0~1 的小数，BM25 的分数可能是 0 到几十，**量纲不同，直接加是错的**。

RRF（Reciprocal Rank Fusion，倒数排名融合）的做法是**只看名次，不看分数**：

```
某个块在向量结果里排第 2 名 → 得分 1 / (60 + 2)
某个块在 BM25 结果里排第 1 名 → 得分 1 / (60 + 1)
两路得分相加 → 重新排序
```

60 是个经验常数，作用是让名次差异被平滑掉（第 1 名和第 2 名不会差太多）。

## 7. 重排（rerank）为什么能再提一档

检索（第 ④ 步）本质是**粗筛**：它把几千个块快速缩到 3~10 个，速度快但粗糙，因为向量是"提前算好的浓缩数字"，细节丢了。

**重排**是精读：把"问题 + 每一块原文"一起送进一个更小的模型（叫 Cross-Encoder），让模型逐字对比打分。慢，但准。

```
粗筛：5000 块 → 20 块（快）
精排：20 块  → 3 块（慢但准）
```

代价是慢（每块都要调一次模型），所以只对少量候选做。

我的参考实现里加了一个务实的细节：**精排服务挂了，就自动降级回粗筛的结果并标记"已降级"**，而不是直接报 500 错误。这叫降级链，是工程能力的体现，答辩时很能说。

## 8. 生成与引用：防幻觉的最后一关

模型天然倾向"把话编圆"，所以要有三道约束：

1. **提示词约束**：只依据给定资料；资料不足时明确说"资料中没有找到相关规定，建议咨询学校相关职能部门"（而不是猜）
2. **要求标注来源**：每条结论后面写 `[1]`，对应第几段资料
3. **后端校验**：回答生成后，用正则把 `[n]` 全抓出来，检查 n 是否 ≤ 资料条数。发现编造的编号就标记出来

第 3 步是"机器抓机器"，纯提示词是靠不住的。这条链路做完整，你的系统就叫**可溯源问答**——这是简历和答辩里最有说服力的词。

## 10. 术语表（一句话版）

| 术语 | 一句话解释 |
|---|---|
| RAG | 先去资料里检索，再让模型照资料回答 |
| 解析 | 从 PDF/Word 里把文字抠出来 |
| 切分 chunk | 把长文切成小块（如 200 字/块） |
| 重叠 overlap | 相邻两块重复的部分，防止把句子切断 |
| 向量 embedding | 把文字变成一串数字，意思近的数字也近 |
| 余弦相似度 | 用两个向量的夹角衡量"有多像" |
| 向量检索 | 按向量距离找最相似的块 |
| BM25 | 按关键词出现频率打分的经典算法 |
| 混合检索 | 向量和 BM25 各查一遍再融合 |
| RRF | 按名次加权融合两路结果（不看原始分数） |
| 重排 rerank | 用更精细的模型给候选块重新打分 |
| 降级 | 某个外部服务挂了，自动退回到次优方案而不是报错 |
| 提示词 prompt | 发给模型的那段文字（含规则、资料、问题） |
| 幻觉 | 模型编造不存在的事实 |
| 引用校验 | 后端检查回答里的 `[n]` 是否真实存在 |
| 可溯源 | 每条结论都能指到原始文件的具体段落 |
| OCR | 从图片里识别文字（扫描件 PDF 用） |
| Spring Boot | Java 的 Web 脚手架：启动服务、接请求、连数据库 |
| 依赖注入 | 你要的对象，框架自动造好给你，不用自己 new |
| MultiPart | 上传文件用的表单格式 |
| SSE | 服务器一点一点往客户端推数据（打字机效果） |

## 12. 三个必须能答上来的问题

**Q1：为什么不用大模型直接回答，要搞 RAG？**
因为模型不知道我校规章、知识有截止时间、会编、给不出处。RAG 把"查资料"和"写答案"分开，便宜、可更新、可溯源。

**Q2：为什么切 200 字，不切 500 或 50？**
切太大一块里混多个主题，检索不准、浪费上下文；切太小一句话被切散，模型看不懂。这个数不是拍脑袋，是我在论文里用不同参数跑评测选出来的（Recall@3、MRR 对比）。

**Q3：你的系统怎么保证不瞎编？**
三层：提示词限定"只依据资料、不足就说不知道"；强制标注 `[n]` 出处；后端正则校验编号真实存在。另外评测里算"幻觉率"。
