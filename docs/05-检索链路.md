## 混合检索：为什么不是纯向量

> 出处：原 `docs/05-混合检索.md`（已合并，正文未改写）

> 时间：2026-11-22
> 目标：解决"列举型问题向量检索漏块"的问题
> 结论先说：**混合检索修好了一类问题，但没修好全部。** 下面有实测数字。

---

### 1. 为什么加 BM25

之前只用向量检索，问「违纪处分有哪几种」，Top3 是：

```
1. 《违纪处分条例》#15  0.6361
2. 《违纪处分条例》#2   0.6134
3. 《违纪处分条例》#23  0.5997
```

文档选对了，但**含答案清单的那一块（#3："…给予下列之一的处分：（1）警告；（2）严重警告；（3）记过；（4）留校察看；（5）开除学籍"）连 Top10 都没进**。

原因：向量比的是"整体意思像不像"。问题里“有哪几种”这个意图，在向量空间里会被稀释——#2 是总则，满篇"违纪处分"，反而最像。

BM25 是**按字面命中**打分的老算法（1994 年），它只关心一件事：**问题里的词，在这块里出现了几次、这个词在全库有多稀有**。

---

### 2. BM25 的公式（三个直觉就够了）

```
分数 = Σ 每个查询词： IDF × (词频 × (K1+1)) / (词频 + K1 × (1 - B + B × 块长/平均块长))
```

| 认识 | 直觉 |
|---|---|
| **IDF**（逆文档频率） | 词越稀有越值钱。"学生"几乎每块都有 → 不值钱；"留校察看"只有几块有 → 很值钱 |
| **TF 饱和** | 一个词出现 5 次比 1 次重要，但**不会**重要 5 倍。公式里分子分母都有词频，天然饱和 |
| **长度归一化** | 长块天生容易命中更多词，要按长度折价。`B` 控制折价强度 |

我们取的参数（业界通用默认值，**没有为本语料调过**）：

```java
K1 = 1.5   // 词频饱和速度
B  = 0.75  // 长度归一化强度（0=不归一化，1=完全归一化）
```

> 这两个数是"可调实验参数"。以后写论文可以做一组 K1 ∈ {1.2, 1.5, 2.0} × B ∈ {0.5, 0.75, 1.0} 的消融。

---

### 3. 中文怎么分词：单字 + 相邻双字

`Tokenizer.tokenize("学生证")` → `学、学生、生、生证、证`

- **单字**：保证召回（只要出现"学"就沾边）
- **双字**：保证精度（"学生"比单独的"学"更有意义）

**为什么不用 jieba / IK？**
1. 要加载几十 MB 词典，多一个依赖、多一个出错点
2. bigram 在"短问题 vs 短块"这个场景上效果已接近真分词
3. 想换的话只改 `Tokenizer` 一个类，BM25 那边不用动（这就叫接口隔离）

---

### 4. 怎么把两路合起来：RRF

```
fused[块] = w向量 / (60 + 向量名次) + wBM25 / (60 + BM25名次)
```

- **为什么用名次不用分数**：余弦是 0~1，BM25 是 0~30+，直接相加等于 BM25 一家说了算
- **为什么 k = 60**：把名次差距压平。第 1 名 1/61、第 2 名 1/62，差距很小 → 不会因为某一路的第一名就完全决定结果
- **权重**：向量 0.2 / BM25 0.8（`campus.retrieval.hybrid-w-vector`，可配置）

---

### 5. 代码地图

| 文件 | 职责 | 关键点 |
|---|---|---|
| `service/Tokenizer.java` | 分词 | 单字 + bigram；`clean()` 只留汉字/字母/数字 |
| `service/Bm25Index.java` | 建索引 + 打分 | 一次遍历建 TF/DF/长度；`scores(query)` 返回与块一一对应的分数数组 |
| `service/RetrievalService.java` | 调度 | `SearchMode` 三值；`prepare()` 只向量化一次、读库一次，三种方式复用；BM25 索引按**指纹缓存** |
| `controller/SearchController.java` | 接口 | `/api/search?mode=`、`/api/search/compare`（三路对比）、`/api/search/stats` |

#### 索引为什么能缓存

建索引要遍历 414 个块（约 8 万 token），每次查询重建会白花几十毫秒。缓存键用**指纹**：`块数:最大块id`。上传/删除文档 → 指纹变 → 自动重建。

```java
// RetrievalService.bm25Index()
if (cached != null && chunksAreSame(cached, chunks)) return cached;  // 复用
Bm25Index.build(chunks);                                            // 重建
```

### 6. 实测（8 个问题 × 3 种方式，Top1 都是对的文档）

| 问题 | 向量 Top1（块/分数） | BM25 Top1（块/分数） | 混合 Top1 |
|---|---|---|---|
| 转专业需要满足什么条件 | #5 / 0.7217 | #23 / 25.99 | #23 |
| 学生证丢了怎么补办 | #2 / 0.7635 | #2 / 22.19 | #2 |
| 辅修专业怎么申请 | #2 / 0.7595 | #2 / 31.40 | #2 |
| 留校察看多少个月 | #4 / 0.6698 | #4 / 43.22 | #4 |
| 旷课多少学时会被处分 | 综合测评#6 / 0.6886 | 综合测评#6 / 21.14 | 综合测评#6 |
| **学业证书有哪些** | **#2** / 0.7317 | **#1** / 26.05 | #1 |
| 学分认定怎么申请 | #8 / 0.7408 | #14 / 24.32 | #8 |
| 提前毕业需要什么条件 | #4 / 0.7559 | #4 / 30.42 | #4 |

**分数不能横着比**：向量是 0~1 余弦，BM25 是 0~30+，混合是 0.016 量级的 RRF 分。要看的是**排名对不对**。

#### 真修好的
- 「学业证书有哪些」：向量给 #2（讲证书性质），BM25 给 **#1（逐条列出证书种类）** —— 这正是列举型问题该命中的块

#### 没修好的
- 「违纪处分有哪几种」：三路都没把 #3（含五种处分清单的那块）捞进 Top3。BM25 进了总则 #1 和解除办法 #13/#0

**这说明混合检索不是银弹。** 这类"聚合型"问题的难点不在算法，而在：
1. 问题里的"哪几种"在原文里不出现 → 字面匹配也没抓手
2. 切分把清单和上下文切开了

正解方向（按性价比排）：
1. **引用原文列给用户**：把 #3 这类块也放进来（召回放宽到 Top10，让模型自己挑）
2. **查询改写**：「违纪处分有哪几种」→「纪律处分的种类」
3. **按条切分 + 块内保留章节标题**

## 精排（Cross-Encoder Rerank）

> 出处：原 `docs/07-精排（Rerank）.md`（已合并，正文未改写）

> 一句话结论：加了精排之后，**Recall@3 从 0.9375 提到 0.9688，MRR 从 0.875 提到 0.9063**，
> 之前那两道"正确块排第 4 名"的 badcase 全部修好；代价是每道题多花约 0.4 秒。
> 数据：414 块 / 36 题（32 道有效）/ topK=3。

---

### 一、为什么要精排

我们原来的检索是**粗排**：把问题和每个块各自变成 1024 维向量，算余弦；BM25 再加一路字面匹配。
它快（一次查询几十毫秒），但只看"像不像"，**不看"这段到底能不能回答这个问题"**。

C 轮评测抓到三道典型的坑（下表的"名次"是**混合 RRF** 下的位置）：

| 题 | 正确块的位置 | 前几名在讲什么 |
|---|---|---|
| #12 国家奖学金一年多少钱 | 第 4 名（chunkId=1473） | 评审程序、申请资格——都提到"国家奖学金"，但**没有金额** |
| #16 综合测评里学业成绩占多大比重 | 第 4 名（chunkId=1279，A 方案前是第 10） | "综合测评"字样更密集，但讲的是评优办法 |
| #19 违纪处分有哪几种 | 已进前 3 | 重新切分后清单不再被劈成两半，BM25 就捞回来了 |

粗排分不清"提到了金额"和"真的写了金额"。这就是精排要解决的事。

### 二、精排和向量检索的本质区别

| | 向量检索（Bi-Encoder） | 精排（Cross-Encoder） |
|---|---|---|
| 怎么算 | 问题和块**各自**编码成向量，再比余弦 | 问题和块**拼在一起**送进模型 |
| 能提前算吗 | 能（入库时把 414 个块都算好） | **不能**，必须一条一条算 |
| 速度 | 一次查询几十毫秒 | 一次调用约 0.4 秒（10 条候选） |
| 准度 | 粗 | 细，能看到"问题里的'多少钱'对上块里的'10000元'" |

所以标准做法是**两阶段**：粗排负责"别漏"（多召回一些），精排负责"排准"（把真正答得上来的顶到前面）。

```
用户问题
   ↓ 粗排：混合 RRF，从 414 块里选出 10 个候选        ← 快
   ↓ 精排：10 条候选逐条送 Cross-Encoder，得相关性分   ← 慢但准
   ↓ 取前 3 条
大模型生成答案 + 引用
```

| `demo/src/main/java/com/campus/rag/config/RerankConfig.java` | 把上面那个类注册进 Spring 容器 |

### 四、关键设计

#### 4.1 为什么要"候选 10 条 → 取前 3"

精排每次调用约 0.4 秒（10 条文档）。如果直接把 414 个块都送进去，光这一题就要十几秒。
而 badcase 告诉我们：**正确块排第 4~10 名**，所以取 10 条候选刚好覆盖。

#### 4.2 为什么失败必须"降级"而不是报错

```java
double[] scores = rerankClient.scores(p.question(), documents);
if (scores == null) {
    // 降级：保持粗排顺序，只截到 topK
    return pool.size() <= topK ? pool : pool.subList(0, topK);
}
```

网络抖动、额度用完、超时都可能发生。这时退回粗排结果——**体验略差，但用户不会看到 500**。
日志会留一条 WARN，方便事后排查。

#### 4.3 为什么 `enabled` 默认 false

开发调试时不希望每问一句都等 0.4 秒。关掉时检索照常工作，只是没有精排这一步。
开的时候在 `application-local.yml` 里写 `campus.rerank.enabled: true`。

### 五、实测结果

#### 5.1 总体（`GET /api/eval/run?topK=3`，32 道有效题，414 块，13.4 秒）

| 配置 | 命中 | Recall@3 | MRR |
|---|---|---|---|
| 纯向量 | 28/32 | 0.8750 | 0.7604 |
| 纯 BM25 | 30/32 | 0.9375 | 0.8385 |
| 混合 RRF | 30/32 | 0.9375 | 0.8750 |
| 混合 RRF（不去重） | 30/32 | 0.9375 | 0.8646 |
| **混合 + 精排** | **31/32** | **0.9688** | **0.9063** |

> 连跑两次，五个配置的数字完全一致（可复现）。

#### 5.2 按题型 Recall@3

| 配置 | 事实型 | 数值型 | 流程型 | 列举型 |
|---|---|---|---|---|
| 纯向量 | 0.8333 | 0.8000 | 1.0 | 1.0 |
| 纯 BM25 | 1.0 | 0.8667 | 1.0 | 1.0 |
| 混合 RRF | 1.0 | 0.8667 | 1.0 | 1.0 |
| **混合 + 精排** | 1.0 | **0.9333** | 1.0 | 1.0 |

精排的收益集中在**数值型**（0.8667 → 0.9333）——正是它擅长的那种"问题里有具体属性、块里有具体数字"的匹配。

#### 5.3 漏题对比

| 配置 | 漏掉的题 |
|---|---|
| 纯向量 | #12 国家奖学金多少钱、#15 一等奖学金多少钱、#17 旷课多少学时、#18 上课迟到怎么算 |
| 纯 BM25 | #12 国家奖学金多少钱、#16 学业成绩占多大比重 |
| 混合 RRF | #12、#16 |
| 混合（不去重） | #12、#16 |
| **混合 + 精排** | #2 一年可以申请几次转专业 |

**精排修好了 #12 和 #16 这两道"正确块在第 4 / 第 10 名"的题**——这正是设计它的目的。

### 六、诚实记录：精排也带来一个新漏题

残存漏题从 2 道降到 1 道，但**新漏了 #2「一年可以申请几次转专业」**。

原因：精排模型只看"问题与单块的相关性"，不看"两块合起来才完整"。
这道题的答案可能落在两个相邻块里，各自看都"不太直接"，于是被精排压到了后面。

**结论**：精排不是银弹。它擅长"从候选里挑出最直接的"，不擅长"拼合分散的信息"。
后者要靠**相邻块合并**（下一步 B 方案）。

5. 语料 17 份、414 块，属小规模；真实校园几千份文件时结论未必成立

## 相邻块合并与展开邻居

> 出处：原 `docs/08-相邻块合并与展开邻居.md`（已合并，正文未改写）

> 记录时间：2026-11-22 下午
> 代码：`RetrievalService.mergedHits()` / `expandHits()` / `joinNeighbors()` / `searchBest()`
> 评测：`GET /api/eval/run?topK=3`（36 题 / 32 道有效 / 414 块 / 9 种配置）

---

### 一、要解决什么问题

切分是机械的。一条规定被切成两块是常态，最典型的例子就在我们自己的语料里：

```
《违纪处分条例》第 5 条
前一块结尾：……给予下列之一的处
后一块开头：改表现，给予下列之一的处分：（1）警告；（2）严重警告；（3）记过；（4）留校察看；（5）开除学籍。
```

- 单看前一块：没有清单
- 单看后一块：有清单，但"什么情形下给处分"这个前提在上一块
- 结果：问「违纪处分有哪几种」，纯向量排第 8 名、混合排第 3 名开外，直接被判定为"没检索到"

**根因不是算法不行，是"一个答案被劈成两半"。** 这类问题有解，而且解法不复杂。

---

### 二、三种做法（我们全试了）

| 做法 | 排序用什么文本 | 给模型看什么文本 | 直觉 |
|---|---|---|---|
| **合并（merge）** | 前一块 + 自己 + 后一块 | 同左 | 排序时就能看到完整句子 |
| **展开（expand）** | 只用自己的块 | 前中后三块 | 排序要精，给模型看要全 |
| **合并 + 精排** | 前中后三块 | 前中后三块 | 两件事一起做 |

代码里对应：

- `mergedHits(p, topK, dedupe, withRerank)` —— 先把三块拼好，再排名（可选精排）
- `expandHits(p, hits)` —— 排名完全不动，只把每条的 `content` 换成三块拼接
- `joinNeighbors(byIndex, index)` —— 拼接的实现，含一个关键细节（见第四节）

### 三、实测结果（本轮最硬的证据）

| 配置 | 命中 | Recall@3 | MRR | 漏题 |
|---|---|---|---|---|
| 纯向量 | 28/32 | 0.8750 | 0.7604 | #12 #15 #17 #18 |
| 纯 BM25 | 30/32 | 0.9375 | 0.8385 | #12 #16 |
| 混合 RRF | 30/32 | 0.9375 | 0.8594 | #12 #16 |
| 混合 RRF（不去重） | 30/32 | 0.9375 | 0.8490 | #12 #16 |
| 混合 + 精排 | 31/32 | 0.9688 | 0.9063 | #2 |
| 混合 + 合并相邻块 | 30/32 | 0.9375 | 0.9219 | #12 #16 |
| 合并相邻块 + 精排 | 31/32 | 0.9688 | 0.9271 | #2 |
| 混合 + 展开邻居 | 30/32 | 0.9375 | 0.9219 | #12 #16 |
| **精排 + 展开邻居（推荐）** | **31/32** | **0.9688** | **0.9375** | #2 |

#### 三条结论

1. **"精排 + 展开邻居"在两个指标上同时最好**（0.9688 / 0.9375）
   → 线上链路就定这个：`searchBest()` = 混合粗排 → Cross-Encoder 精排（单块）→ 展开邻居（内容）
2. **"合并 + 精排" 一开始明显更差（0.9063 / 0.8854）**，原因有两个，都已修/已记录：
   - 三块拼起来后无关内容变多，精排反而被干扰（这是"排序要精"的直接证据）
   - 拼接时把每个邻居块的块头前缀 `【标题 · 章节】` 也带进来，一段里出现三个标题 → 修掉前缀重复后升到 0.9688 / 0.9271
3. **只合并不精排，能提升 MRR（0.8594 → 0.9219）但不提召回**
   → 说明它的价值在"把正确块往前排"，不在"多捞回来"

```
另外，违反校纪校规情节轻微、不足以给予上述处分的，由学生所在学院给予通报批评…… [1]
```

——同一个问题在 B 方案之前是**漏题**（正确块不在 Top3）。**这一条就是 B 方案的全部意义。**

### 四、实现时踩的两个坑（都值得记）

#### 坑 1：拼接时块头前缀重复

`joinNeighbors` 初版就是三段直接拼，结果一段 600 字里有三个 `【文档标题 · 第X章】`，
把正文冲淡、也让精排的注意力跑偏。

修法：邻居块的前缀用正则剥掉，**只有自己那块保留前缀**（它是"这是哪份文件哪一章"的唯一线索）。

```java
private static final Pattern CHUNK_PREFIX = Pattern.compile("^【[^】]*】\\s*");
...
if (sb.length() > 0) {
    text = CHUNK_PREFIX.matcher(text).replaceFirst("");   // 邻居的前缀去掉
}
```

#### 坑 2：两个候选本来就是邻居 → 合并后内容重叠

粗排候选取 10 个，里面常常有 `#3` 和 `#4`（相邻）。
如果各自展开成 `[2,3,4]` 和 `[3,4,5]`，最终 3 条引用里有 2 条在讲同一段话，白占名额。

修法：记一份"每份文档已占用的块区间"，后来的候选区间若与已占用区间重叠就跳过。

#### 附带发现：OCR 噪声会顺着展开被放大

有的扫描页（表格/盖章页）Windows OCR 出来是乱码，例如：

```
一；一．成一员．一一由一各一学一．院．党一组织．书一记一《一．．一学处分管学生资助工作的副处长组成。
```

展开邻居后，这类垃圾文本会进入送给大模型的资料里。
**这属于"语料质量问题"，不是检索问题**，记入待办：对这些页重做 OCR 或人工校正。

## 拒答阈值

> 出处：原 `docs/09-拒答阈值.md`（已合并，正文未改写）

> 记录时间：2026-11-22 晚
> 代码：`RetrievalService.searchBestGated()` / `Best` 记录；`QaService.ask()` 的闸门分支；`SearchController` 的 `mode=best`
> 标定脚本：`tools/calibrate_threshold.py`
> 配置：`campus.retrieval.min-score-rerank`（默认 0.10）、`campus.retrieval.min-score-hybrid`（默认 0，未启用）

---

### 一、要解决什么问题

E 方案之前，库里根本没有的问题（「食堂几点开门」「图书馆能借几本书」）也会走完整条链路：

```
向量化 → 混合检索 → 精排 → 拼提示词 → 调 DeepSeek → 模型靠提示词说"暂未收录"
```

两个坏处：

1. **白花钱**：明知道资料不相关，还是调了一次大模型（约 1.3 秒 + 一次 token 费用）
2. **多一次编造机会**：模型手里有 3 个不相关的块，提示词只能"劝"它别用，劝不住就编

正确做法：**在检索层就判断"资料够不够"**，不够就直接回话，不问模型。这叫"宁可说没查到，也不猜"。

---

### 二、怎么判断"够不够"——用哪个分数

系统里有两个分数，**量纲差 20 倍，绝不能共用一个阈值**：

| 分数 | 量级 | 说明 |
|---|---|---|
| 精排分（Cross-Encoder） | 0 ~ 1，真能答上来的常见 0.5~0.99 | 「问题 + 这一段」一起送进模型，输出"这一段能回答这个问题的概率" |
| 混合 RRF 分 | 0.0x（两路都排第一也只有 0.0328） | Σ 权重/(60+名次)，只反映"名次好不好"，不反映"内容对不对" |

所以我们配两个：

```yaml
min-score-rerank: 0.10    # 开精排时用这个（当前生效）
min-score-hybrid: 0.0     # 关精排时用这个（还没标定，先不启用）
```

---

### 三、标定：36 道题 + 8 道探针，用数据定阈值

#### 方法

```powershell
python tools\calibrate_threshold.py 8090   # 逐题调 /api/search?mode=best，取 topScore
```

脚本做三件事：逐题取最高分 → 按"可答 / 库里没有"两组排序 → **扫描 0.20~0.65 每个阈值会误拒几道、放过几道**。

#### 实测分布

| 组 | 题数 | 分数范围 |
|---|---|---|
| 可答题 | 32 | 最低 **0.2004**（#29 毕业要修满多少学分），最高 0.9976 |
| 库里没有（题集里的 4 道） | 4 | 最高 **0.0025**（#35 食堂几点开门），最低 0.0016 |

**两组之间有 80 倍的间隔**，说明精排分是真的能区分"有没有资料"，不是玄学。

#### 阈值扫描

| 阈值 | 误拒（可答题被判没资料） | 放过（无答案题混进来） |
|---|---|---|
| 0.20 | 0 | 0 |
| 0.25 | 3 | 0 |
| 0.40 | 3 | 0 |
| 0.55 | 6 | 0 |
| 0.65 | 9 | 0 |

**结论：取 0.10**。
理由：0 误拒、4 道无答案题全拦；离可答题最低分（0.2004）还有 0.10 的安全余量，语料扩充后不容易误伤。
取 0.20 也能 0 误拒，但离边界太近——样本只有 32 道，边界值随时会被新题打破。

### 四、8 道"探针题"：暴露了阈值的真实边界

标定时我额外问了 8 个题集里没有的问题，看分数落在哪：

| 问题 | 精排分 | 闸门 | 实际情况 |
|---|---|---|---|
| 图书馆开放时间是什么 | 0.0030 | 🚫 拦 | 库里确实没有 ✅ |
| 食堂一顿饭多少钱 | 0.0031 | 🚫 拦 | 库里确实没有 ✅ |
| 宿舍楼晚上几点关门 | 0.0023 | 🚫 拦 | 库里确实没有 ✅ |
| 宿舍可以用电吹风吗 | 0.0117 | 🚫 拦 | 库里确实没有 ✅ |
| 晚上超过门禁时间回宿舍怎么办 | 0.0511 | 🚫 拦 | 库里确实没有 ✅ |
| 学生证补办要多少钱 | 0.1435 | ✅ 放 | 规定里写了"需缴纳工本费"但没写金额 → 该放行，让模型说"没写金额" |
| 补考还不及格怎么办 | 0.4411 | ✅ 放 | 学籍规定里有重修条款 → 该放行 |
| **旷课多少学时会被处分** | **0.8929** | ✅ 放 | ⚠️ 库里**没有**学时标准（原文指向一份我们没收的文件）→ **分数闸门拦不住** |

#### 这一行是重点，也是局限

「旷课多少学时」拿到 0.89 分，因为库里有大量"旷课""处分"相关内容，只是**具体数字没有**。
分数闸门只能判断"主题在不在库里"，判断不了"具体那条答案在不在库里"。

所以拒答是**两层**的：

| 层 | 管什么 | 我们的做法 |
|---|---|---|
| 检索层（本方案） | 主题都不在库里 → 不问模型 | 精排分 < 0.10 直接拒答 |
| 生成层（已有） | 主题在、细节缺 → 让模型说"没写" | 提示词第 2/6 条 + 收录范围清单 |

## 自适应融合权重（被证伪）

> 出处：原 `docs/13-自适应权重实验.md`（已合并，正文未改写）

> 目的：修掉「硬改写题上固定权重反噬」这个现象。
> 结论先写在最前面：**机制有效，但效应量只有 1~2 道题，在当前 98 道题上还不足以宣称显著**。

---

### 1. 要修的问题

融合权重一直是写死的：

```yaml
campus.retrieval.hybrid-w-vector: 0.2   # 向量 0.2 / BM25 0.8
```

第 6 轮扩题后暴露了后果（100 题，硬改写 10 道）：

| 配置 | 硬改写 Recall@3 |
|---|---|
| 纯向量 | 60% |
| 纯 BM25 | **20%** |
| 混合 RRF（0.2 / 0.8） | **40%** |

**混合反而比纯向量还差**。原因是硬改写题几乎不与原文共享汉字（题面与原文平均字面重叠 0.23，4 道为 0.00），BM25 在整个库上都打不出有意义的分数，那 0.8 的权重等于把噪声加权后按到向量排对的块头上。

### 2. 机制

#### 2.1 信号怎么算

```
signal = BM25 最高分 ÷ 查询词数
```

为什么除以词数：BM25 分是所有查询词得分的**和**，问题越长分越高。直接拿绝对分数卡阈值，长问题永远"信号强"、短问题永远"信号弱"。除以词数（本项目分词 = 单字 + 相邻双字）才可比。

#### 2.2 判据与动作

```
signal ≥ bm25-strong-avg  →  维持默认 0.2 / 0.8（BM25 确实对得上字面）
signal <  bm25-strong-avg  →  向量权重上调到 0.7（BM25 只剩 0.3）
```

实现位置：`demo/src/main/java/com/campus/rag/service/RetrievalService.java`

- `record WeightDecision(double wVector, double wBm25, double signal, String reason)`
- `WeightDecision decideWeights(Prepared p)`
- `rrf(double[] v, double[] b, double wVector)` 重载
- 调试接口 `GET /api/search/weights?q=...` → 返回 signal 与本次决策（标定用）
- `GET /api/search/stats` 会回显 `adaptive / bm25StrongAvg / weakWVector`，可确认配置是否真的生效

配置项：

| 配置 | 默认 | 含义 |
|---|---|---|
| `campus.retrieval.adaptive` | `false` | 总开关（默认关闭，见第 5 节） |
| `campus.retrieval.bm25-strong-avg` | `1.5` | 判"信号足够"的门槛 |
| `campus.retrieval.weak-w-vector` | `0.7` | 信号弱时的向量权重 |

### 3. 标定：信号到底能不能把题分开

| 改写型 | 11 | 0.96 | 1.60 | 2.29 |

| 无答案 | 2 | 0.89 | 0.97 | 1.04 |

阈值扫描（把多少题判成"BM25 弱"）：

### 4. 实测（98 道有效题 / 643 块 / 同一份题集、同一份语料）

|---|---|---|---|---|---|---|

| 自适应 T=1.3 | 93.88% | 0.8810 | 94.23% | 93.48% | 70% | 0.5833 |
| 自适应 T=1.5 | **94.90%** | **0.8912** | 94.23% | **95.65%** | 70% | 0.5833 |

各配置在硬改写上的召回（同一批 10 道题）：

| 配置 | 基线 | T=1.3 | T=1.5 |
|---|---|---|---|
| 纯向量 | 60% | 60% | 60% |
| 纯 BM25 | 20% | 20% | 20% |
| 混合 RRF | 40% | **60%** | **60%** |
| 混合（不去重） | 50% | 60% | 60% |
| 混合 + 精排 | 40% | 60% | 60% |
| 混合 + 合并相邻块 | 50% | 60% | 60% |
| 合并相邻块 + 精排 | 60% | 60% | 60% |
| 混合 + 展开邻居 | 50% | 60% | 60% |
| **精排 + 展开（线上）** | 60% | **70%** | **70%** |

按题型看，线上链路**只有硬改写这一栏动了**（60% → 70%），数值型 / 事实型 / 流程型 / 列举型 / 改写型全部不变。

### 5. 诚实结论：只多对了 1~2 道题

这是本次实验最重要的一段：

- 硬改写 10 道题，从 6 道对变 7 道对 —— **实际翻转的只有 1 道题**（#98「病历丢了能补吗」）。
- 在 **dev 集上完全没变化**（94.23% 一样，MRR 甚至从 0.8942 掉到 0.8910）。
- test 上从 42/46 到 44/46（T=1.5），也就是 2 道题。
- 46 道题里多对 2 道 = 4.3 个百分点，**但它的置信区间宽到没有区分能力**（二项分布：46 题、p≈0.91，±2 题完全在抖动范围内）。

所以：

> **不能写"自适应权重把 Recall 从 92.86% 提到 94.90%"——那是把 2 道题说成 2.04 个百分点。**

能写的只有：**在 10 道硬改写题上，固定权重使混合检索比纯向量更差（40% vs 60%），加入信号判断后混合回到 60%、线上链路到 70%；但受题量限制，该改进尚未达到可宣称的显著性。**

因为收益未经证实，**默认关闭**（`campus.retrieval.adaptive: false`）。打开方式：

```
mvn spring-boot:run -Dspring-boot.run.arguments="--server.port=8090 --campus.retrieval.adaptive=true"
```

### 6. 五条局限

1. 硬改写题只有 10 道，效应量（1~2 道）与噪声同量级。
2. 阈值是**二段式**（要么 0.2 要么 0.7），真实信号是连续的；更平滑的做法是按 signal 线性插值权重。
3. `signal` 依赖分词粒度：换成 jieba/IK 分词后同一条题目的 signal 会变，阈值需要重新标定。
4. dev 集信号分布与 test 集不完全一致（test 的硬改写题信号偏高），说明"硬改写"这个标签本身还不够客观。
5. 只做了单变量（权重）实验，没验证"权重 + 精排候选数"的交互。

2. 权重由二段式改线性插值：`wVector = clamp(0.7 - (signal - 1.0) * k, 0.2, 0.7)`，用 dev 定 k。

## 查询改写与双查询融合

> 出处：原 `docs/14-查询改写.md`（已合并，正文未改写）

> 一句话：检索之前，先用大模型把「借的书忘还了怎么算」翻译成「所借图书逾期未归还将如何计算处理」，
> 再去做 BM25。**硬改写题召回 70% → 80%，总召回 89.83% → 92.37%。**

---

### 1. 为什么加这一步

系统有两个"看不出来但很致命"的短板，都来自同一件事：**用户不说文件的词**。

| 用户说 | 文件说 | 字面检索结果 |
|---|---|---|
| 忘还了怎么算 | 逾期未归还 | 0 分 |
| 被记过多久能消 | 处分期限届满可申请解除 | 0 分 |
| 帮人答到 | 代替他人参加考试（代考） | 0 分 |
| 挂科 | 课程考核不合格 | 低分 |
| 点蜡烛 | 使用明火 | 0 分 |

30 道硬改写题的基线：纯 BM25 只有 **46.7%**、线上链路 **70%**。
这不是算法不行，是**词没对上**——而这是真实用户（尤其新生）最常见的问法。

### 2. 为什么用大模型，而不是同义词表

同义词表只能覆盖写死的词对，学生说法是无穷的。但**大模型只做翻译，不做检索**：

| 环节 | 谁干 | 处理的数据量 |
|---|---|---|
| 口语 → 书面语 | 大模型，1 句话 | ~60 输入 token / ~30 输出 token |
| 在 643 个块里找 | 还是向量 + BM25 | 24 万字 |

所以"向量被替代"是误解：**语义筛选still由向量做，大模型只把问题翻译成向量能理解的词**。

### 3. 成本控制：不是每次都调

| 手段 | 做法 | 效果 |
|---|---|---|
| **信号触发** | 先算 BM25 信号（免费），`signal < 1.5` 才改写 | 只有约 25% 的请求会调大模型 |
| **结果缓存** | 同一问句第二次直接命中缓存 | 重复问题 0 成本、0 延迟 |
| **超短输出** | `max_tokens=96`、只允许输出一句话 | 单次成本 ≈ ¥0.0004 |
| **失败降级** | 改写失败返回 null，检索退回原句 | 改写不会成为新故障点 |

对比整条链路：生成答案要 ~1300 输入 + 300 输出 token（≈¥0.005），
改写只占 **不到 10%**。

### 11. 双查询融合：修掉"改写把对的题弄坏"

#### 11.1 做法

改写只换了 BM25 那一路，等于"押注改写一定对"。一旦改写跑偏，原本能命中的块就被挤掉（#54 就是这么坏的）。

改成**两个问句都算数**：

```
原句   → BM25 排名 r1 ┐
                       ├→ RRF 合并 → 融合后的 BM25 分 ─┐
改写句 → BM25 排名 r2 ┘                                ├→ 混合 RRF → 精排 → 展开
原句   → 向量排名 ─────────────────────────────────────┘
```

融合发生在 BM25 这一路**内部**，所以后面的"混合 RRF → 精排 → 展开"完全不动。

#### 11.2 一个关键参数：融合权重

`campus.rewrite.fusion-w-rewritten`（默认 **0.5**）= 改写句在融合里占的权重。

| 取值 | 结果 |
|---|---|
| 0.2（复用向量权重） | "混合 + 双查询融合" = 80.51%，**和纯混合一模一样** → 融合几乎等于只用原句，白做 |
| **0.5（各占一半）** | "混合 + 双查询融合" = 83.05%（比纯混合 +2.5pt），硬改写 46.7% → 53.3% |

结论：**复用别的环节的权重是最容易犯的错**，每个权重量纲不同，必须单独给默认值并单独验证。

#### 11.3 实测（118 道有效题 / 643 块 / 13 种配置 / 212 秒）

| 配置 | 总 Recall@3 | 总 MRR | 硬改写(30) | dev | test |
|---|---|---|---|---|---|
| 精排 + 展开邻居（原线上） | 89.83% | 0.8333 | 70.0% | 93.55% | 85.71% |
| 混合 + 查询改写 | 86.44% | 0.7669 | 66.7% | 88.71% | 83.93% |
| 改写 + 精排 + 展开 | 89.83% | 0.8475 | 73.3% | 93.55% | 85.71% |
| 混合 + 双查询融合 | 83.05% | 0.7500 | 53.3% | 88.71% | 76.79% |
| **双查询融合 + 精排 + 展开（新线上）** | **90.68%** | **0.8531** | **76.7%** | **95.16%** | 85.71% |

- 硬改写：70.0% → 73.3%（只改写）→ **76.7%（融合）**，30 道里 21 → 22 → 23 道
- dev 涨 1.6 个点，test 与基线持平 → 没有牺牲一侧
- 融合把 #54 救回来了（"改写 + 精排 + 展开"的漏题里有 54，融合那路没有）

#### 11.4 必须承认的波动

同一份代码、同一份语料，改写相关的那两路在三次运行里分别是：

| 运行 | 改写 + 精排 + 展开 |
|---|---|
| 第 1 次 | 92.37%（27/118 漏） |
| 第 2 次 | 90.68% |
| 第 3 次（本次，含融合） | 89.83% |

原因是改写要调大模型，1 次失败就会退化成"没用改写"。
所以这次加了 `GET /api/search/rewrite-stats`：

```
attempts=118  successes=117  failures=1  cacheHits=0
```

**报数规矩**：以后凡是带"改写"的数字，必须同时给出 attempts/successes/failures，
否则读者无法判断这次是真有效还是没跑成。论文里也要写"三次运行的波动范围 ±1~2 道题"。

#### 11.5 局限

1. 融合权重 0.5 只在一份 100 题题集上定，没做更细的扫描（0.3/0.4/0.5/0.6/0.7）。
2. 两个问句都会调一次 BM25 全量打分（643 块 × 2），延迟从 ~7ms 涨到 ~10ms，可忽略但要知道。
3. 融合只在 BM25 内部做；没有做"改写句也走向量"（那会把向量也污染，暂不做）。
