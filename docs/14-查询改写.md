# 查询改写（Query Rewrite）：把学生的话翻译成规章的话

> 一句话：检索之前，先用大模型把「借的书忘还了怎么算」翻译成「所借图书逾期未归还将如何计算处理」，
> 再去做 BM25。**硬改写题召回 70% → 80%，总召回 89.83% → 92.37%。**

---

## 1. 为什么加这一步

系统有两个"看不出来但很致命"的短板，都来自同一件事：**用户不说文件的词**。

| 用户说 | 文件说 | 字面检索结果 |
|---|---|---|
| 忘还了怎么算 | 逾期未归还 | 0 分 |
| 被记过多久能消 | 处分期限届满可申请解除 | 0 分 |
| 帮人答到 | 代替他人参加考试（代考） | 0 分 |
| 挂科 | 课程考核不合格 | 低分 |
| 点蜡烛 | 使用明火 | 0 分 |

30 道硬改写题的基线：纯 BM25 只有 **46.7%**、线上链路 **70%**。
这不是算法不行，是**词没对上**——而这是真实用户（尤其新生）最常见的问法。

## 2. 为什么用大模型，而不是同义词表

同义词表只能覆盖写死的词对，学生说法是无穷的。但**大模型只做翻译，不做检索**：

| 环节 | 谁干 | 处理的数据量 |
|---|---|---|
| 口语 → 书面语 | 大模型，1 句话 | ~60 输入 token / ~30 输出 token |
| 在 643 个块里找 | 还是向量 + BM25 | 24 万字 |

所以"向量被替代"是误解：**语义筛选still由向量做，大模型只把问题翻译成向量能理解的词**。

## 3. 成本控制：不是每次都调

| 手段 | 做法 | 效果 |
|---|---|---|
| **信号触发** | 先算 BM25 信号（免费），`signal < 1.5` 才改写 | 只有约 25% 的请求会调大模型 |
| **结果缓存** | 同一问句第二次直接命中缓存 | 重复问题 0 成本、0 延迟 |
| **超短输出** | `max_tokens=96`、只允许输出一句话 | 单次成本 ≈ ¥0.0004 |
| **失败降级** | 改写失败返回 null，检索退回原句 | 改写不会成为新故障点 |

对比整条链路：生成答案要 ~1300 输入 + 300 输出 token（≈¥0.005），
改写只占 **不到 10%**。

## 4. 代码位置

| 文件 | 作用 |
|---|---|
| `demo/src/main/java/com/campus/rag/service/QueryRewriter.java` | 改写器本体：提示词、温度 0、缓存、清洗、失败降级 |
| `QueryRewriter.RewriteResponse` | 极简响应壳（只要 `choices[0].message.content`） |
| `RetrievalService#searchBestGated` | **生产路径**：信号 < 阈值时才改写，改完重算 BM25 分，向量路仍用原句 |
| `RetrievalService#withRewrittenBm25` | 复用同一次读库/向量化结果，只重算 BM25 |
| `RetrievalService.EVAL_VARIANTS` | 新增两路评测配置：`hybrid_rewrite`、`rewrite_rerank_expand` |
| `SearchController#/api/search/rewrite` | 调试入口：看原句、改写句、信号 |

配置（`application.yml`）：

```yaml
campus:
  rewrite:
    enabled: ${REWRITE_ENABLED:false}   # 默认关；关掉时行为与之前完全一致
    timeout-seconds: 8
    cache-size: 500
```

> 顺手修掉一个真 bug：`adaptive` / `bm25-strong-avg` / `weak-w-vector` 三项之前误写在
> `campus:` 下（应该是 `campus.retrieval:`），等于配置文件里那三行从来没生效过，
> 一直是靠 `@Value` 的默认值在跑。

| 纯 BM25 | 77.12% | 0.6822 | 46.7% | — | — |

## 7. 这次和「自适应权重」那次有什么区别

上次自适应权重：dev 零变化、只在 test 涨 2 道 → 结论是"收益未证"，默认关闭。

这次查询改写：**dev +2 道、test +1 道，两边都涨**，且方向一致（都是硬改写题），
说明它不是噪声，是真实机制。但依然只有 +3 道，**不能吹成"提升 4 个点"**。

诚实的写法：

> 在 30 道硬改写题上，查询改写使 Recall@3 从 70.0% 提升到 80.0%（21/30 → 24/30，净 +3 道），
> dev/test 两个划分同时提升；总集召回从 89.83% 提升到 92.37%（净 +3 道）。

## 8. 已知局限

1. **会弄坏原本答对的题**（#54）：改写引入了原文没有的词，把正确块挤掉了。
   → 后续可做"双查询融合"：原句 BM25 + 改写句 BM25 各排一次，RRF 合并，降低单点风险。
2. 改写质量依赖模型。DeepSeek 表现稳定，但换模型需重新抽查一批。
3. 提示词里没有"规章术语表"，模型靠通用知识翻译，遇到本校特有词（如"三自"社区）可能翻译不准。
4. 目前只在检索前用一次，没有做"多轮对话里的指代改写"（那是上下文管理的活）。
5. 逐题只 +3 道，样本仍偏小；要更有说服力需要 100 道以上硬改写题。

## 11. 双查询融合：修掉"改写把对的题弄坏"

### 11.1 做法

改写只换了 BM25 那一路，等于"押注改写一定对"。一旦改写跑偏，原本能命中的块就被挤掉（#54 就是这么坏的）。

改成**两个问句都算数**：

```
原句   → BM25 排名 r1 ┐
                       ├→ RRF 合并 → 融合后的 BM25 分 ─┐
改写句 → BM25 排名 r2 ┘                                ├→ 混合 RRF → 精排 → 展开
原句   → 向量排名 ─────────────────────────────────────┘
```

融合发生在 BM25 这一路**内部**，所以后面的"混合 RRF → 精排 → 展开"完全不动。

### 11.2 一个关键参数：融合权重

`campus.rewrite.fusion-w-rewritten`（默认 **0.5**）= 改写句在融合里占的权重。

| 取值 | 结果 |
|---|---|
| 0.2（复用向量权重） | "混合 + 双查询融合" = 80.51%，**和纯混合一模一样** → 融合几乎等于只用原句，白做 |
| **0.5（各占一半）** | "混合 + 双查询融合" = 83.05%（比纯混合 +2.5pt），硬改写 46.7% → 53.3% |

结论：**复用别的环节的权重是最容易犯的错**，每个权重量纲不同，必须单独给默认值并单独验证。

### 11.3 实测（118 道有效题 / 643 块 / 13 种配置 / 212 秒）

| 配置 | 总 Recall@3 | 总 MRR | 硬改写(30) | dev | test |
|---|---|---|---|---|---|
| 精排 + 展开邻居（原线上） | 89.83% | 0.8333 | 70.0% | 93.55% | 85.71% |
| 混合 + 查询改写 | 86.44% | 0.7669 | 66.7% | 88.71% | 83.93% |
| 改写 + 精排 + 展开 | 89.83% | 0.8475 | 73.3% | 93.55% | 85.71% |
| 混合 + 双查询融合 | 83.05% | 0.7500 | 53.3% | 88.71% | 76.79% |
| **双查询融合 + 精排 + 展开（新线上）** | **90.68%** | **0.8531** | **76.7%** | **95.16%** | 85.71% |

- 硬改写：70.0% → 73.3%（只改写）→ **76.7%（融合）**，30 道里 21 → 22 → 23 道
- dev 涨 1.6 个点，test 与基线持平 → 没有牺牲一侧
- 融合把 #54 救回来了（"改写 + 精排 + 展开"的漏题里有 54，融合那路没有）

### 11.4 必须承认的波动

同一份代码、同一份语料，改写相关的那两路在三次运行里分别是：

| 运行 | 改写 + 精排 + 展开 |
|---|---|
| 第 1 次 | 92.37%（27/118 漏） |
| 第 2 次 | 90.68% |
| 第 3 次（本次，含融合） | 89.83% |

原因是改写要调大模型，1 次失败就会退化成"没用改写"。
所以这次加了 `GET /api/search/rewrite-stats`：

```
attempts=118  successes=117  failures=1  cacheHits=0
```

**报数规矩**：以后凡是带"改写"的数字，必须同时给出 attempts/successes/failures，
否则读者无法判断这次是真有效还是没跑成。论文里也要写"三次运行的波动范围 ±1~2 道题"。

### 11.5 局限

1. 融合权重 0.5 只在一份 100 题题集上定，没做更细的扫描（0.3/0.4/0.5/0.6/0.7）。
2. 两个问句都会调一次 BM25 全量打分（643 块 × 2），延迟从 ~7ms 涨到 ~10ms，可忽略但要知道。
3. 融合只在 BM25 内部做；没有做"改写句也走向量"（那会把向量也污染，暂不做）。
