# 项目讲解与自测手册

> 用法：这份文档不是给面试官看的，是给**你自己**用的。
> 目标——任何一天被临时叫去面谈，能在 5 分钟内把系统讲到"有数据、有取舍、有边界"。
> 全部代码位置都是当前仓库真实行号，可现场打开指给面试官看。

## 一、三层讲述法

同一个项目要准备三个长度，视对方给的时间切换。**千万别用 15 分钟版本去回答"介绍一下你的项目"。**

### 第 1 层：30 秒（电梯版）

> "一个校园规章制度的智能问答系统。学生用大白话问'旷课多少学时会被处分'，系统从 33 份校内规章（643 个文本块、约 24 万字）里检索出相关条款，让大模型**照着原文回答**，每条答案都带引用编号，能点开看到原文块。
> 它有两个硬指标：检索 Recall@3 做到 90.68%；端到端答对率 51.7%（严格口径）、含部分正确 78.8%，幻觉率从 48.3% 压到 34.7%。
> 技术栈 Spring Boot 3.5 + MySQL + Vue 3，单 jar 部署。"

（数字全部可复现：评测看板一点就重跑。）

### 第 2 层：3 分钟（演示版）

按 `docs/18-演示脚本.md` 走一遍：问答（流式 + 引用 + 接地标签）→ 拒答演示 → 文档管理（切块可见）→ 检索调试（五路对比）→ 评测看板（13 配置）。
**讲述主线**：先说"它能答"，再说"它凭什么可信"，最后说"我怎么知道它做得好不好"。

### 第 3 层：15 分钟（深聊版）

按下面第 2 节的链路，从 HTTP 入口一路讲到底层检索，中间穿插第 5 节的"为什么这么设计"。

## 二、一条请求的完整链路（面试核心，必须能背）

以「旷课多少学时会被处分？」为例，走 `/api/qa/stream`：

| # | 做什么 | 代码位置 |
|---|---|---|
| 1 | 鉴权拦截：识别令牌里的 uid/role，管理类前缀校验 | `config/AuthInterceptor.java:62` |
| 2 | 解析会话：没给 sessionId 就新建（标题取问题前 20 字），给了就校验归属 | `controller/QaController.java` → `service/SessionAccess.java:35` |
| 3 | 载入历史：最近 3 轮、单条截 120 字、总量 600 字、抹掉历史里的 `[n]` 防抄错编号 | `service/ContextAssembler.java:70` |
| 4 | **第 0 步：追问补全**——先按原句检索，分数 < 0.30 且有历史时，让模型补全成完整问句再检索一次，**只有分数更高才采用** | `service/QaService.java:210` → `service/QueryRewriter.java:168` |
| 5 | **检索**：查询改写（可选）→ 向量 + BM25 双路 → RRF 融合 → 相邻块去重 → Cross-Encoder 精排 Top3 → 展开邻居 | `service/RetrievalService.java:572` |
| 6 | **两层拒答**：检索层（精排分 < 0.015 直接拒答，不调模型）→ 生成层（提示词要求资料不足时说"未查到"） | `service/RetrievalService.java:572` 尾部闸门 + `PromptBuilder.java:43` |
| 7 | **拼 Prompt**：8 条系统规则 + 【知识库收录范围】+【资料 [n]】+【对话历史】+【提问】 | `service/PromptBuilder.java:43,87` |
| 8 | **生成**：SSE 流式，逐 token 推给前端；先发 `sources`（查到哪几条）再发 `token` | `service/ChatClient.java:133` → `QaService.java:185` |
| 9 | **引用校验**：正则抽答案里的 `[n]`，检查编号是否真实存在、是否越界 | `service/QaService.java:271` |
| 10 | **接地校验**：把答案里的硬事实（数字+单位、期限、处分等级）抽出来，逐条在被引用块原文里做包含判断 | `service/AnswerGuard.java:164` |
| 11 | 落库：user/assistant 两条消息，assistant 存全部校验信号 + 引用快照 JSON | `controller/QaController.java` → `service/SessionDao.java` |

**一句话总结链路**：
> 先定"问的是什么"（历史 + 补全），再定"看哪几段"（混合检索 + 精排 + 展开），再定"怎么答"（8 条规则 + 流式），最后定"答得靠不靠谱"（引用校验 + 接地校验）。

## 四、数据模型（5 张表，为什么这么设计）

| 表 | 作用 | 关键设计点 |
|---|---|---|
| `kb_document` | 文档元数据 + 状态机 | `status`(待处理/成功/失败) 让入库可重试；`stored_name` 与原始文件名分离 |
| `kb_chunk` | 块 + 向量 | `embedding LONGTEXT` 存 JSON 数组；复合索引 `(document_id)` 加速按文档补向量；643 块规模下暴力余弦就够，不引向量库 |
| `qa_session` | 会话 | `user_id` 做数据隔离；`idx_user_update(user_id, update_time)` 贴合"我的会话按时间倒序" |
| `qa_message` | 消息 | `references_json` 存**当时的**引用快照——语料换了以后重新检索会错位，"当时看到什么就存什么" |
| `sys_user` | 用户 | `password_hash` + 每用户随机盐；`uk_username` 唯一；不存明文、不返盐 |

**为什么只有 5 张表？** 因为评测题、评测结果都放文件（`data/testset/eval_questions.tsv`），它们是研发资产不是运行时数据；放库里反而要写一套管理界面。

## 六、自测题（28 道，先自己答，再对照要点）

### A 组：链路与原理（面试必问）

1. **为什么用 RAG 而不是微调？**
   要点：知识更新频繁（规章每年改）、要溯源、要可拒答；微调解决"风格/能力"不解决"事实归属"，且成本高、更新难。
2. **为什么切 220 字、重叠 50 字？**
   要点：220 字≈一个完整条款；重叠防"一句话被切成两半后两半都不完整"；实测 748 碎块→305 块。
3. **块头为什么要补【文档·章节】？**
   要点：块脱离上下文后，模型不知道"第十三条"属于哪一章；补前缀让单块自带归属，检索也能命中章节词。
4. **BM25 为什么用 bigram？**
   要点：中文没空格，单字切分噪声大；bigram（单字+双字）在 643 块规模上实测比纯向量好（77.12% vs 76.27%）。
5. **RRF 是什么？为什么用它而不是加权求和？**
   要点：RRF 只看排名不看分数，天然解决"余弦 0~1、BM25 0~几十"尺度不可比；k=60 抑制头部。
6. **精排（Cross-Encoder）和向量检索的本质区别？**
   要点：向量是"双塔"分别编码后算距离（快、粗）；Cross-Encoder 把 query+doc 拼一起过模型（慢、准）。所以两级：先召回 10 再精排 3。
7. **为什么要"展开邻居"？**
   要点：排序用单块最准，但给模型看需要上下文；答案跨块时（前半在第 k 块、后半在第 k+1 块）不展开就会答一半。
8. **阈值 0.015 怎么定的？**
   要点：扫一遍 118 道应答题 + 2 道库外题的 topScore 分布，取"误拒最少且能拦住库外题"的点；**注意它是链路属性**——加了展开邻居后分数被稀释，从 0.10 改成 0.015。
9. **为什么拒答要放在检索层，而不是让模型自己说不知道？**
   要点：快（0.44s vs 1.7s）、省 token、可控；模型"帮忙本能"会硬编。
10. **引用校验和接地校验有什么区别？**
    要点：引用校验防"编造不存在的编号"（格式/范围）；接地校验防"编号真实但内容编造"（答案里的数字必须在被引原文出现过）。

### B 组：取舍与负结果（区分"做过"和"想过"）

11. **自适应融合权重为什么关掉？**
    要点：想法是 BM25 信号弱就加大向量权重；实测只多对 1~2 道、dev 集零变化，收益不抵复杂度 → 默认 false，代码留着。
12. **两段式生成为什么关掉？**
    要点：先摘原句再只用原句组答案；幻觉 34.7%→31.4%，但误拒 5.1%→9.3%、延迟 1.4→2.1s、答对率没涨 → 零和，默认 false。
13. **为什么不做"把模型答案写进向量库"？**
    要点：用模型输出洗模型输入，错误会被固化；且污染评测集。正解是人工核实后进"补充库"。
14. **你说 badcase 65% 在生成层，怎么得出的？**
    要点：643 块算每题的"库内命中块数" + `topK=10` 看正确块排名 → A(4~10)、A2(未召回)、D(已在 Top3)、BC(库里没有)。结果 D=30/46、A2=10、A=6、BC=0 → 推翻"缺知识"的猜测。
15. **流式为什么不让首字更快？**
    要点：首字延迟里 1.0~1.4s 是检索（改写+精排），流式只优化"生成阶段"的观感与 TTFT；想再压要动检索链路。
16. **为什么不用向量数据库？**
    要点：643 块、1024 维，暴力余弦几十毫秒；Milvus/pgvector 是为百万级准备的。README 的"已知局限"里写明了什么时候该换。

### C 组：工程与安全（考"是不是只会写 demo"）

17. **为什么要异步评测任务？**
    要点：一轮 225 秒，浏览器/网关会超时，且没有进度；改成 POST 提交 + 轮询快照 + 单线程排队（避免并发抢精排接口）。
18. **流式为什么必须用独立线程池？**
    要点：长连接会占满 Tomcat 工作线程；用专用固定线程池，客户端断开由 emitter 生命周期处理。
19. **数据隔离怎么做的？**
    要点：归属写在 `qa_session.user_id`；判定压成纯函数 `SessionAccess.can(owner, requester, isAdmin)`；越权返回"会话不存在"而不是 403（不泄露 id 存在性）。
20. **评测脚本也会写对话库吗？**
    要点：会，曾经灌了 162 条垃圾会话；后来加 `X-No-Persist` 头给机器调用走显式旁路。
21. **JWT 为什么手写？**
    要点：少一个依赖 + 与项目"关键算法手写"风格一致；但明确记录局限：不能吊销、SHA-256 弱于 BCrypt。
22. **前端拦截了，后端还要不要校验？**
    要点：前端是体验（菜单隐藏、路由守卫），后端才是安全；两层都要有。
23. **`schema.sql` 会不会自动建表？**
    要点：不会。它只有 `CREATE TABLE IF NOT EXISTS`，改动结构必须单独跑 migration（踩过坑：加了 `sys_user` 没建表直接启动失败）。

### D 组：边界与反思（考成熟度）

24. **51.7% 正确率会不会太低？**
    要点：严格口径必须答全；含部分正确 78.8%；把 42 个点拆成检索 9.3 / 加料 32.2 / 误拒 5.1 / 真错 5.1，主战场在生成层。
25. **多轮只有 8 组样本，能说明什么？**
    要点：不能下结论，只能当方向性证据（单轮 Top1 38% → 带历史 100%）；扩到 30 组才敢写进论文。
26. **你的评测集是不是自己出题自己调参？**
    要点：是（承认过拟合风险）；已经拆 dev/test，且 test 集数字比 dev 低约 9pt，说明没有只挑好看的。
27. **上线前还差什么？**
    要点：Key 环境变量注入、阈值换语料重标、启动冒烟测试、压测出 QPS/P95、失败重试与超时策略。
28. **如果给你一个月继续做，最先做什么？**
    要点：生成层（证据宽度 / 上下文组织）＞ 压测与可运维性 ＞ 多轮扩样本 ＞ 查询分解。

## 七、五个"深水区"追问（能答出来就是加分）

1. **精排服务的延迟占多少？不可用时用户体感如何？**
   → 检索总耗时约 1.0~1.4s，精排是大头；不可用时自动降级为 RRF 顺序，接口不中断，只是精度降（有降级日志）。
2. **如果两个块内容冲突（新旧规章），怎么处理？**
   → 当前靠"文档级"覆盖 + 检索分数排序，没有显式的时效字段——这是已知缺口，正解是给 `kb_document` 加生效日期，冲突时按日期优先。
3. **SSE 断线了怎么办？**
   → 目前不续传，只能重发（`Last-Event-ID` 机制没做）；这是已知局限，做的话要给 emitter 加事件 id 和缓冲。
4. **embedding 换了模型怎么办？**
   → 换模型等于全部重算：`kb_chunk.embedding` 是模型相关产物，要有"配置指纹"记录当前模型，指纹变了就全量重嵌（当前靠手工 `embed-all`）。
5. **怎么保证上线后不退化？**
   → 现在靠人跑评测看板；正解是把 dev/test 评测接进 CI，改检索/提示词后自动出对比表。

## 八、三天复习法

- **Day 1（链路）**：把第 2 节 11 步抄一遍，然后打开代码逐个点进去看，看不懂的就在旁边写一句人话注释。目标：合上文档能复述链路。
- **Day 2（取舍）**：只看 B、C 组 13 道题，每题写三行：想法 / 数据 / 结论。目标：能讲清 4 个负结果。
- **Day 3（演练）**：按 `docs/18-演示脚本.md` 对着镜子讲两遍 3 分钟版；再随机抽 A、D 组 10 题自问自答。

> 判断"我到底懂了没"的标准只有一条：**能不能不用看代码，说出一次请求里数据长什么样、经过了谁。**
